## 2. 产品概述

### 2.1 问题陈述

校园开放日 AI 实践工作坊需要从现在开始收集学生报名，由管理员集中审核。若依靠线下表格或人工消息收集，会出现重复报名、身份无法识别、审核名额超限、状态无法追踪、服务重启后数据丢失等问题。

本系统提供一个轻量、可部署、可验收的报名与审核闭环：学生使用教学用虚构学号登录并提交报名申请，管理员查看申请和名额统计后进行通过或驳回，系统负责身份去重、名额约束、状态持久化和审计记录。

### 2.2 产品目标

1. 让教师能够通过服务器 IP 和端口直接打开系统并完成完整验收。
2. 让学生在 1 分钟内完成登录、填写和提交报名。
3. 保证同一活动中同一学号最多存在一条报名申请。
4. 保证审核通过人数永远不超过 100 人，即使多人同时审核。
5. 让管理员能够准确看到活动信息、申请列表、总数、审核余量和报名理由。
6. 在服务重启后保留报名和审核结果，不丢失已提交数据。
7. 通过清晰的状态、错误提示和验证记录降低验收成本。

### 2.3 成功标准

- 教师使用学生测试账号可以完成一次成功报名，并查看“待审核”结果。
- 教师使用相同学号重复提交时，不会产生第二条申请，页面能说明重复原因。
- 教师使用管理员测试账号可以看到总报名数、已通过数、剩余审核名额、报名理由和操作结果。
- 通过操作达到 100 人后，后续通过操作被拒绝并保留为待审核，不会突破上限。
- 使用不同学号但相同姓名的学生可以分别报名。
- 服务重启后，已有申请及审核状态与重启前一致。
- 未登录用户不能访问报名结果或管理员数据，学生不能调用管理员操作。
- 提交文档、源代码、部署说明、测试记录和访问信息后，教师可独立完成验收。

## 3. 范围定义

### 3.1 MVP 必须包含

- 学生测试身份登录。
- 管理员登录和登出。
- 当前活动信息展示。
- 学生报名页面和管理员管理页面。
- 学生报名表单和字段校验。
- 报名申请创建和本人结果查询。
- 同学号唯一约束与重复提交处理。
- 管理员申请列表、状态筛选和基础分页。
- 报名总数、待审核数、已通过数、已驳回数和剩余审核名额。
- 管理员通过或驳回申请。
- 100 人通过上限及并发场景下的事务保护。
- 数据库持久化、服务重启恢复和健康检查。
- 基本权限控制、错误提示、审计日志和部署文档。

### 3.2 本版本不做

- 真实校园统一身份认证、教务系统对接或短信验证。
- 学生注册、找回密码、手机号绑定和真实身份核验。
- 多个活动同时运营、复杂活动配置和多租户。
- 报名材料上传、支付、签到、通知消息和证书发放。
- 管理员批量审核、导出 Excel、复杂报表和数据分析。
- 管理员自助创建账号或修改权限。
- 移动端原生 App；采用响应式 Web 满足移动浏览器访问。
- 面向互联网大规模流量的分布式部署。

## 4. 用户身份与权限

### 4.1 身份定义

| 身份 | 是否产品登录身份 | 核心目标 | 数据范围 |
| --- | --- | --- | --- |
| 未登录访客 | 否 | 打开系统、选择登录方式、看到必要的活动说明 | 公开活动基本信息和登录入口 |
| 学生申请人 | 是 | 提交一次报名并查看自己的结果 | 只能读写自己的报名申请 |
| 活动管理员 | 是 | 统计、审核和追踪所有申请 | 可读取和审核本活动全部申请 |
| 教师验收者 | 否，使用测试账号验收 | 验证学生端和管理员端是否满足作业要求 | 不额外拥有业务权限 |
| 部署/运维者 | 非业务身份 | 配置测试账号、启动服务、备份和恢复 | 通过部署环境管理，不通过前台业务页面操作 |
| 系统服务 | 非人类用户 | 执行认证、校验、持久化、并发控制和审计 | 按服务端规则访问数据库 |

### 4.2 身份识别原则

1. 学号是学生身份的唯一业务键，必须先规范化再比较，例如去除首尾空格；是否大小写不敏感应在实现中固定并写入测试。
2. 姓名只用于展示和报名快照，不参与判定是否重复报名。
3. 两个不同学号即使姓名相同，也视为两个不同学生。
4. 同一学号即使第二次提交时修改姓名，也必须命中原申请，不能绕过唯一约束。
5. 题目明确测试账号为虚构账号，因此系统不宣称提供真实校园身份认证。
6. 学生测试身份应使用部署配置或种子数据维护，未知或停用学号必须拒绝登录。
7. 管理员账号与学生学号分离，不能因为知道学号而获得管理员权限。

## 5. 关键业务规则

### 5.1 活动规则

- 活动名称：校园开放日 AI 实践工作坊。
- 活动日期：部署时以明确的 event_date 配置为准，当前分析暂定 2026-11-21。
- 通过容量：100 人。
- “剩余可审核名额”定义为 capacity - approved_count，最低为 0。
- 待审核申请可以超过 100 条；限制的是“审核通过人数”，不是申请总人数。

### 5.2 报名规则

- 学号、姓名、报名理由均为必填项。
- 学号必须匹配已配置的有效测试身份。
- 姓名应去除首尾空格，禁止空白姓名；长度和允许字符集应在实现中统一校验。
- 报名理由应去除首尾空格，禁止空理由，并设置合理的最大长度以防止异常大请求。
- 同一活动中 event_id 与 student_id 的组合必须唯一。
- 报名提交成功后状态为 pending，不可由学生自行改为通过或驳回。
- 学生再次提交时返回原申请状态或明确的重复提交错误，不创建新记录。
- 学生不能查看其他学号的报名记录。

### 5.3 审核规则

- 只有 pending 申请可以被审核。
- 管理员可以通过或驳回待审核申请。
- 通过操作必须在事务中检查并占用名额；并发审核时最终通过数不得超过 100。
- 当已通过人数达到 100 时，新的通过操作返回“名额已满”，申请保持 pending，管理员仍可驳回其他待审核申请。
- MVP 不允许学生重新报名；已驳回记录仍占用该学号的一次报名资格。
- MVP 不提供已通过到待审核、已驳回到待审核的反向流转，避免重复审核和计数歧义。
- 每次审核应记录操作者、时间、原状态、目标状态和失败原因（如适用）。

### 5.4 状态模型

~~~text
未提交
  └─提交成功→ pending
pending
  ├─管理员通过→ approved
  └─管理员驳回→ rejected
~~~

终态说明：approved 和 rejected 均为终态；同一学生不能通过再次提交回到 pending。

## 6. 用户场景与用例

### UC-01 学生登录并查看活动

**参与者**：学生申请人、系统服务  
**前置条件**：系统可用；学生测试身份已配置。  
**主流程**：

1. 学生打开服务器 IP 和端口对应的地址。
2. 选择“学生登录”。
3. 输入测试学号并提交。
4. 系统规范化学号并校验其是否为有效身份。
5. 校验通过后创建学生会话，展示活动名称、日期、容量和当前本人状态。

**异常流程**：

- 学号为空：提示必填，不发起业务请求。
- 学号不存在或已停用：返回“测试身份无效”，不泄露其他有效学号信息。
- 学生已登录后访问管理员路径：返回未授权或跳转到学生首页。

**验收结果**：有效学生能进入自己的报名页；无效学生无法创建会话。

### UC-02 学生提交报名申请

**参与者**：学生申请人、系统服务、数据库  
**前置条件**：学生已登录；当前活动处于接受报名状态。  
**主流程**：

1. 学生填写姓名和报名理由。
2. 系统校验字段格式、长度和必填项。
3. 系统在事务中按学号检查唯一申请。
4. 没有历史申请时创建记录，状态为 pending。
5. 返回申请编号和“已提交，等待审核”状态。

**异常流程**：

- 字段校验失败：标记具体字段，不创建记录。
- 已存在申请：不创建第二条记录，展示当前申请状态和提交时间。
- 网络超时后客户端重试：通过唯一约束和可选幂等键保证不重复。
- 数据库不可用：返回服务暂不可用，不能向用户显示“提交成功”。

### UC-03 学生查看报名结果

**参与者**：学生申请人  
**主流程**：

1. 学生登录后进入“我的报名”。
2. 系统按当前会话中的学生身份查询申请。
3. 展示活动信息、本人提交内容、状态、提交时间和审核时间。
4. pending 展示等待审核；approved 展示报名成功；rejected 展示审核未通过。

**安全约束**：查询必须使用会话中的学生 ID，不接受前端传入任意 student ID 作为唯一授权依据。

### UC-04 管理员登录并查看仪表盘

**参与者**：活动管理员、系统服务  
**前置条件**：管理员测试账号已配置。  
**主流程**：

1. 管理员选择“管理员登录”。
2. 输入管理员账号和密码。
3. 系统完成认证并建立管理员会话。
4. 展示活动名称、活动日期、容量、报名总数、待审核数、已通过数、已驳回数和剩余名额。
5. 展示申请列表，默认按提交时间倒序。

**异常流程**：

- 凭证错误：返回统一错误，不区分账号不存在或密码错误。
- 登录失败过多：按 IP 和账号进行限流或临时锁定。
- 学生会话访问管理员 API：返回 403，不返回管理数据。

### UC-05 管理员查看和筛选申请

**参与者**：活动管理员  
**主流程**：

1. 管理员按状态筛选 pending、approved 或 rejected。
2. 查看学号、姓名、报名理由、提交时间、状态和审核信息。
3. 通过分页继续读取较长列表。
4. 进入申请详情查看完整理由和审计信息。

**数据展示约束**：报名理由必须完整可读；列表字段不能暴露密码、会话令牌等非业务字段。

### UC-06 管理员通过申请

**参与者**：活动管理员、系统服务、数据库  
**前置条件**：管理员已登录；申请状态为 pending。  
**主流程**：

1. 管理员点击“通过”。
2. 服务端开启短事务并锁定活动容量计数或使用等价的原子约束。
3. 服务端重新读取已通过数量。
4. 若小于 100，将申请改为 approved，写入审核人和审核时间。
5. 提交事务并刷新统计数据。

**名额已满流程**：

- 若已通过数量为 100，事务回滚申请状态更新，返回 QUOTA_FULL。
- 前端提示“通过名额已满”，申请仍为待审核，管理员可选择驳回。

### UC-07 管理员驳回申请

**参与者**：活动管理员  
**前置条件**：管理员已登录；申请状态为 pending。  
**主流程**：

1. 管理员点击“驳回”。
2. 系统要求确认，必要时填写内部审核备注。
3. 系统将状态改为 rejected，记录审核人和时间。
4. 学生下一次查看时看到审核未通过。

### UC-08 教师通过 IP 完成验收

**参与者**：教师验收者  
**主流程**：

1. 访问 http://<服务器IP>:<端口>。
2. 使用学生测试账号验证报名、重复提交和结果查看。
3. 使用管理员测试账号验证统计、理由展示、通过、驳回和名额已满。
4. 重启服务后再次查询，确认数据仍在。
5. 根据验收记录检查异常场景与部署文档。

**验收要求**：不能依赖本机 hosts、域名、开发服务器临时状态或未提交的本地数据库。

### 8.1 页面状态要求

每个需要请求数据的页面至少包含以下状态：

- 初始加载：显示明确的加载状态。
- 成功有数据：显示完整内容和下一步操作。
- 成功无数据：显示空态和原因，不显示空白页面。
- 参数错误：指出具体字段及修复方式。
- 权限错误：说明需要的身份，并提供返回或重新登录入口。
- 服务错误：显示可理解的错误信息和重试动作，不显示堆栈。
- 提交中：禁用重复提交控件，避免用户误触发多次请求。

## 9. 数据方案

### 9.1 核心实体

~~~text
events
  id, name, event_date, capacity, status, created_at, updated_at

student_identities
  id, student_no, display_name, active, created_at

admin_accounts
  id, username, password_hash, active, created_at, updated_at

applications
  id, event_id, student_id, submitted_name, reason, status,
  reviewed_by, reviewed_at, review_note, created_at, updated_at

sessions
  id, subject_type, subject_id, token_hash, expires_at, created_at

audit_logs
  id, actor_type, actor_id, action, target_type, target_id,
  metadata_json, request_id, created_at
~~~

### 9.2 约束与索引

- student_identities.student_no 唯一。
- applications(event_id, student_id) 唯一，作为防重复报名的最终保障。
- applications.status 仅允许 pending、approved、rejected。
- events.capacity 必须为正整数，当前值为 100。
- applications.reviewed_by 只能引用管理员账号或为空。
- 为 applications(event_id, status, created_at) 建索引，支持管理员筛选和排序。
- 为 applications(event_id, student_id) 建唯一索引，保证并发请求下仍只能有一条记录。
- 密码只保存成熟算法生成的哈希，不能保存明文。
- 申请理由和审核备注按文本字段保存，不应通过拼接 SQL 写入。

### 9.3 统计口径

| 指标 | 定义 |
| --- | --- |
| 报名总数 | 当前活动所有 applications 数量 |
| 待审核数 | status = pending 的申请数 |
| 已通过数 | status = approved 的申请数 |
| 已驳回数 | status = rejected 的申请数 |
| 剩余可审核名额 | max(capacity - approved_count, 0) |

统计必须由数据库查询或事务内可靠计算得到，不依赖前端本地累加。

## 10. 接口方案

接口统一使用 /api/v1 前缀，使用 JSON 请求和响应；错误响应包含机器可识别的 code、人类可读的 message、字段级 details 和 requestId。

| 方法 | 路径 | 权限 | 说明 | 主要状态码 |
| --- | --- | --- | --- | --- |
| GET | /api/v1/health | 公开 | 服务健康检查 | 200/503 |
| GET | /api/v1/events/current | 公开 | 获取当前活动信息 | 200 |
| POST | /api/v1/auth/student/login | 公开 | 学生测试身份登录 | 200/401/429 |
| POST | /api/v1/auth/admin/login | 公开 | 管理员登录 | 200/401/429 |
| POST | /api/v1/auth/logout | 已登录 | 注销当前会话 | 204/401 |
| GET | /api/v1/me | 已登录 | 获取当前会话身份 | 200/401 |
| POST | /api/v1/applications | 学生 | 创建本人申请 | 201/401/409/422 |
| GET | /api/v1/applications/me | 学生 | 查询本人申请 | 200/401/404 |
| GET | /api/v1/admin/dashboard | 管理员 | 获取统计数据 | 200/401/403 |
| GET | /api/v1/admin/applications | 管理员 | 分页、筛选申请 | 200/401/403 |
| GET | /api/v1/admin/applications/:id | 管理员 | 查看申请详情 | 200/401/403/404 |
| POST | /api/v1/admin/applications/:id/approve | 管理员 | 通过申请 | 200/403/404/409 |
| POST | /api/v1/admin/applications/:id/reject | 管理员 | 驳回申请 | 200/403/404/409/422 |

### 10.1 关键错误码

| 错误码 | 含义 | HTTP 状态 |
| --- | --- | --- |
| UNAUTHENTICATED | 未登录或会话失效 | 401 |
| FORBIDDEN | 已登录但无该权限 | 403 |
| INVALID_STUDENT_ID | 学生测试身份无效 | 401 |
| VALIDATION_FAILED | 字段校验失败 | 422 |
| ALREADY_APPLIED | 该学号已有申请 | 409 |
| APPLICATION_NOT_PENDING | 申请已被处理 | 409 |
| QUOTA_FULL | 通过名额已满 | 409 |
| RESOURCE_NOT_FOUND | 申请或活动不存在 | 404 |
| RATE_LIMITED | 请求过于频繁 | 429 |
| SERVICE_UNAVAILABLE | 服务或数据库暂不可用 | 503 |

### 10.2 并发处理要求

管理员通过接口不能采用“先查询数量、再更新申请”的无锁流程。推荐在同一数据库事务中：

1. 锁定活动配置行或等价的容量资源。
2. 查询当前 approved 数量。
3. 小于容量时更新申请，否则返回 QUOTA_FULL。
4. 写入审计日志并提交事务。

同一学号的并发报名依靠唯一索引和事务错误处理；第二个请求必须得到可理解的重复报名结果。

## 11. 非功能需求

### 11.1 可访问性与兼容性

- 支持常见桌面浏览器和移动浏览器的响应式布局。
- 表单字段有可见标签、错误提示和键盘可操作顺序。
- 颜色不能是唯一的状态表达方式，应同时展示文字或图标。
- 按钮在请求期间有禁用和反馈状态，避免重复操作。
- 服务器 IP 直接访问时页面、静态资源和 API 均使用同一可访问地址。

### 11.2 性能与容量

- 在课程验收规模下，常规查询和提交接口目标为 P95 小于 1 秒。
- 系统至少支持 100 个已通过名额及超过 100 条待审核申请。
- 管理员列表必须分页，不能默认无上限读取所有记录。
- 报名和审核事务应短小，不在数据库事务内执行外部网络调用。

### 11.3 可靠性

- 服务重启不应清空数据库。
- 数据库迁移和种子数据应可重复执行或明确失败原因。
- 提供 /api/v1/health，至少区分服务进程正常和数据库不可用。
- 关键错误记录 requestId，方便教师反馈问题时定位请求。
- 部署文档需包含启动、停止、日志查看、备份和回滚步骤。

### 11.4 安全性

- 管理员密码使用成熟密码哈希，不写入前端和 Git。
- 会话使用 HttpOnly、SameSite 和适当有效期；生产环境使用 HTTPS 时启用 Secure。
- 所有管理员 API 在服务端进行认证和角色授权。
- 学生查询使用会话身份，防止通过修改 URL 或参数读取他人申请。
- 输入统一校验，数据库访问使用参数化查询或 ORM。
- 登录按 IP 和账号限流，错误提示不区分账号不存在和密码错误。
- 日志不得记录密码、会话令牌或完整敏感凭据。
- 生产配置通过环境变量传入，提供安全的默认失败行为。

## 12. 验收与测试方案

### 12.1 功能验收矩阵

| 编号 | 场景 | 前置数据 | 操作 | 预期结果 |
| --- | --- | --- | --- | --- |
| T-01 | 正常报名 | 有效学生 A，无申请 | 登录并提交合法姓名和理由 | 新建一条 pending 申请 |
| T-02 | 学生查看结果 | A 已提交 | 进入我的报名 | 只看到 A 的申请和 pending 状态 |
| T-03 | 重复报名 | A 已有申请 | A 再次提交 | 返回 ALREADY_APPLIED，不增加记录 |
| T-04 | 修改姓名绕过 | A 已有申请 | A 使用不同姓名再次提交 | 仍按学号判重，不增加记录 |
| T-05 | 同名不同人 | B、C 学号不同，姓名相同 | B、C 分别提交 | 两条独立申请 |
| T-06 | 无效身份 | 学号 X 不在测试名单 | 尝试登录 | 登录失败，不创建申请 |

| T-09 | 通过申请 | pending 且未满 100 | 管理员点击通过 | 状态 approved，通过数加一 |
| T-10 | 驳回申请 | pending | 管理员点击驳回 | 状态 rejected，并记录审核信息 |
| T-11 | 名额已满 | approved 已有 100 | 通过第 101 条 pending | 返回 QUOTA_FULL，仍为 pending |
| T-12 | 已处理申请重复操作 | approved 或 rejected | 再次审核 | 返回 APPLICATION_NOT_PENDING，不改变结果 |

## 15. 产品决策与待确认项

### 15.1 已确定的方案

| 决策 | 方案 | 原因 |
| --- | --- | --- |
| 学生身份键 | 规范化后的学号 | 满足一次报名和改名场景 |
| 姓名语义 | 报名时的展示快照 | 不让姓名变化绕过唯一约束 |
| 容量口径 | 只限制 approved 数量 | 允许先收集申请，再按名额审核 |
| 重复提交 | 返回原申请，不创建第二条 | 保证幂等和用户可理解性 |
| 审核并发 | 事务锁或等价原子约束 | 保证不超过 100 人 |
| 身份真实性 | 虚构测试身份，不接真实校园认证 | 符合作业边界 |
| 页面访问 | IP + 端口 | 满足教师直接访问要求 |

### 15.2 开发前需要确认

1. 最终活动日期是否确认为 2026-11-21，还是由教师提供其他日期。
2. 学生测试身份名单和管理员测试账号的具体值。
3. 部署服务器操作系统、可用端口和数据库部署方式。
4. 是否允许管理员填写内部驳回备注，以及教师是否需要看到该备注。
5. 是否需要把“报名停止”作为可配置状态；MVP 可先固定为开放。
6. 教师是否要求 HTTPS；若只提供 IP 访问，证书和浏览器安全提示需在部署说明中解释。

## 16. 结论

本方案将作业收敛为一个单活动、双业务角色、强一致性约束的报名审核系统。产品验收的核心不是页面数量，而是四个闭环：

1. 学生身份可识别，且同一学号只能有一条申请。
2. 管理员能够看全量申请并做出明确审核决定。
3. 并发情况下通过人数仍不超过 100 人。
4. 教师通过服务器 IP 可以完整复现、验证并理解系统行为。

后续开发应以本文件的 P0 需求和 T-01 至 T-18 测试矩阵为基线；新增功能必须先判断是否影响 MVP 范围、数据模型、权限和验收路径。
