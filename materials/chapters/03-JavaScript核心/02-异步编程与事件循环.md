# 02 · 异步编程与事件循环

## 一、为什么需要异步

JavaScript 在主线程上单线程执行：一次只能做一件事。如果网络请求、文件读取、定时器都同步阻塞，页面就会卡死。
于是浏览器与 Node 把「耗时操作」交给其他线程或系统，完成后把回调排进队列，等主线程空闲再执行。

## 二、事件循环：一次完整的循环

见 `assets/event-loop.svg`。核心规则只有一条：

> **每执行完一个宏任务，就把所有微任务清空，然后再取下一个宏任务。**

| 队列 | 典型来源 | 优先级 |
| --- | --- | --- |
| 调用栈 | 同步代码 | 最高，先执行完 |
| 微任务队列 | `Promise.then`、`queueMicrotask`、`MutationObserver` | 高于宏任务 |
| 宏任务队列 | `setTimeout`、`setInterval`、I/O、事件回调 | 每轮取一个 |

```js
console.log('1 同步');
setTimeout(() => console.log('4 宏任务'), 0);
Promise.resolve().then(() => console.log('3 微任务'));
console.log('2 同步');

// 输出顺序：1 同步 → 2 同步 → 3 微任务 → 4 宏任务
```

## 三、Promise 状态机与组合子

Promise 只有三种状态：`pending` → `fulfilled` 或 `rejected`，且**状态一旦改变不可逆**。

| 组合子 | 行为 | 适用 |
| --- | --- | --- |
| `Promise.all` | 全部成功才成功，任一失败即失败 | 并发取多个必需数据 |
| `Promise.allSettled` | 等全部结束，返回每个的结果与状态 | 允许部分失败 |
| `Promise.race` | 第一个结束的（无论成败）决定结果 | 超时控制 |
| `Promise.any` | 第一个成功的决定结果 | 多源竞速容灾 |

```js
// 并发请求三个接口，任一失败即整体失败
const [user, orders, coupons] = await Promise.all([
  fetchUser(id),
  fetchOrders(id),
  fetchCoupons(id),
]);

// 允许部分失败：始终能拿到结果，自行判断哪些失败
const results = await Promise.allSettled([fetchA(), fetchB()]);
const okValues = results.filter(r => r.status === 'fulfilled').map(r => r.value);

// 超时控制
const timeout = (ms) => new Promise((_, reject) =>
  setTimeout(() => reject(new Error('请求超时')), ms));
await Promise.race([fetchData(), timeout(3000)]);
```

## 四、async / await 的正确写法

```js
async function loadDashboard(id) {
  try {
    const user = await fetchUser(id);
    const orders = await fetchOrders(id);      // 依赖 user 时才串行
    return { user, orders };
  } catch (err) {
    console.error('加载失败', err);
    throw err;                                  // 交给调用方决定如何提示
  } finally {
    hideLoading();
  }
}
```

**串行 vs 并发**（性能差异巨大，务必分清）：

```js
// 错误：3 个请求依次等待，总耗时 = 三次之和
const a = await fetchA();
const b = await fetchB();
const c = await fetchC();

// 正确：无依赖关系时并发，总耗时 ≈ 最慢的那个
const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()]);
```

## 五、fetch 与错误处理

`fetch` 有个反直觉之处：**HTTP 404／500 不会 reject**，只有网络层失败才 reject。

```js
async function request(url, options = {}) {
  const res = await fetch(url, {
    ...options,
    headers: { 'Content-Type': 'application/json', ...options.headers },
  });

  if (!res.ok) {
    const detail = await res.text().catch(() => '');
    throw new Error(`HTTP ${res.status}: ${res.statusText} ${detail}`);
  }
  return res.status === 204 ? null : res.json();
}

// 取消请求
const controller = new AbortController();
request('/api/slow', { signal: controller.signal });
controller.abort();     // 抛出 AbortError，需在 catch 中识别并忽略
```

## 六、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 请求失败但没走进 `catch` | `fetch` 对 4xx/5xx 不 reject | 手动判断 `res.ok` |
| `forEach` 里写 `await` 无效 | `forEach` 不等待异步回调 | 改用 `for...of` 或 `Promise.all(map)` |
| 循环里 `await` 很慢 | 把并发写成了串行 | 无依赖时改 `Promise.all` |
| 未处理的 Promise 拒绝导致进程退出（Node） | 缺少 catch | 加 `unhandledRejection` 兜底并修根因 |
| `async` 函数返回 `undefined` 被当成成功 | 忘记 return／throw | 明确返回值语义 |
| 组件卸载后 setState 报警 | 异步回来后组件已销毁 | 用取消（AbortController）或挂载标记 |
