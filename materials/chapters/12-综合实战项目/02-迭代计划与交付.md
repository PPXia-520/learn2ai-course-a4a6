# 02 · 迭代计划与交付

## 一、把项目拆成能在一周内完成的迭代

| 迭代 | 目标 | 可演示产出 |
| --- | --- | --- |
| 第 1 轮 | 跑通最小闭环 | 登录 + 创建一条记录 + 列表展示（数据存库） |
| 第 2 轮 | 核心业务完整 | 完整表单校验、行项目计算、编辑与删除 |
| 第 3 轮 | 体验与正确性 | 加载／错误／空态、分页筛选、关键测试 |
| 第 4 轮 | 交付与打磨 | 部署上线、CI 全绿、文档与演示材料 |

**每个迭代都必须包含：能运行的代码 + 能演示的路径 + 更新的文档。** 只有代码没有演示，等于没做完。

## 二、任务拆分：把故事拆到 4 小时以内

```text
故事：编辑报价单并自动计算金额
 ├─ 后端：PATCH /quotes/:id 接口 + 校验 schema（2h）
 ├─ 后端：行项目金额与总计的计算函数 + 单元测试（2h）
 ├─ 前端：编辑表单组件 + 行项目增删（3h）
 ├─ 前端：金额实时计算与格式化显示（1.5h）
 ├─ 联调：错误码映射与提示文案（1.5h）
 └─ 测试：接口成功/失败用例 + 表单校验用例（2h）
```

**拆分标准**：每一项都能独立提交、独立验证、4 小时内能完成。拆不出来的任务说明你还没想清楚。

## 三、进度管理：三个必备板单

| 板单 | 内容 | 更新频率 |
| --- | --- | --- |
| 待办 | 已拆分、未开始的任务 | 每天 |
| 进行中 | 正在做的（同时不超过 2 项） | 每天 |
| 阻塞 | 卡住的任务 + 卡点 + 需要谁帮忙 | 遇到即记 |

**两周法则**：同一件事卡住超过 2 天，必须换方案或求助。硬扛是最大的时间浪费。

## 四、质量红线（不能等到最后才做）

| 项目 | 何时做 | 门槛 |
| --- | --- | --- |
| 类型检查 | 每轮 | 零错误，零 `any` |
| 静态检查 | 每轮 | 零警告 |
| 核心路径测试 | 第 2 轮起 | 关键业务函数与接口有成对用例 |
| CI 流水线 | 第 3 轮 | 四步串联，主干全绿 |
| 安全自查 | 第 3 轮 | 密码哈希、权限校验、输入校验三件套齐全 |
| 部署与回滚 | 第 4 轮 | 有公网地址，回滚演练通过 |

## 五、交付物清单

```text
项目仓库/
  README.md              # 是什么、怎么跑、怎么测、怎么部署（10 分钟上手）
  docs/
    requirements.md      # 问题陈述、用户故事、验收标准、不做清单
    design.md            # 架构图、数据模型、接口清单、ADR 记录
    deployment.md        # 环境要求、配置项、部署与回滚步骤
  src/                   # 前端与后端代码
  tests/                 # 单元 / 集成 / E2E
  infra/                 # Dockerfile、compose、流水线配置
  demo/
    screenshots/         # 关键界面截图
    script.md            # 演示脚本（5 分钟）
```

| 交付物 | 验收方式 |
| --- | --- |
| README | 让一个没参与的人照着跑起来，不问你任何问题 |
| 设计文档 | 别人读完后能画出你的架构图 |
| 自动化测试 | 一条命令跑完，报告可读 |
| 部署 | 公网可访问，有健康检查与回滚方式 |
| 演示材料 | 5 分钟讲清问题、方案、难点、结果 |

## 六、上线前的检查清单

- [ ] 生产环境配置来自环境变量，密钥不在仓库里。
- [ ] 数据库迁移可执行且有备份。
- [ ] 关键接口有健康检查与错误监控。
- [ ] 日志含 requestId，能定位单次请求。
- [ ] 已配置限流，防止被刷。
- [ ] 有回滚方案并演练过一次。
- [ ] 冒烟测试脚本可在部署后立即执行。

## 七、演示与复盘

**5 分钟演示脚本结构**：

| 时间 | 内容 |
| --- | --- |
| 0:00–0:30 | 问题：谁遇到了什么麻烦 |
| 0:30–2:30 | 演示：走一遍核心流程（真实数据，别用 lorem ipsum） |
| 2:30–4:00 | 技术：架构一句话 + 一个最难的坑与解法 |
| 4:00–5:00 | 结果与下一步：数据／反馈／已知不足 |

**复盘三问**：
1. 哪个决定事后看是错的？当时为什么那么决定？
2. 哪一步比我预期花了更久？下次怎么提前发现？
3. 如果重做，我会保留什么、改掉什么？

## 八、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 最后一轮才发现跑不起来 | 没有每轮都部署验证 | 第 1 轮就部署一次 |
| 演示时手忙脚乱 | 没有演示脚本 | 提前写脚本并彩排一次 |
| 文档全靠记忆补写 | 结束时才写文档 | 每轮结束更新对应文档 |
| README 只有一句「项目介绍」 | 没人按它跑过 | 找个同学照着跑一遍并记录他卡住的地方 |
| 上线后出问题不会回滚 | 未演练 | 第 4 轮必做回滚演练 |

## 九、动手练习

1. 把你的项目拆成 4 轮迭代，每轮写出「可演示产出」。
2. 为第 1 轮拆分任务，每项标注预估工时。
3. 写出 README 的第一版，并请他人照做一次，记录他卡住的步骤。
4. 写一份 5 分钟演示脚本，并实际计时讲一遍。
