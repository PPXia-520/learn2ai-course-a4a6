# 01 · 需求分析与技术选型

## 一、从想法到需求：三步收敛

1. **写问题陈述**：谁、在什么场景、遇到什么麻烦、现在怎么凑合。
   > 例：「自由职业者接项目时，报价单靠 Excel 手工填，容易算错且难追溯历史报价。」
2. **写用户故事**：`作为 <角色>，我希望 <能力>，以便 <价值>`。
3. **写验收标准**：可执行、可判定，最好写成「给定 → 当 → 那么」的形式。

```text
用户故事：作为自由职业者，我希望把报价项按模板生成报价单，以便 5 分钟内发出报价。

验收标准：
- 给定已选择模板，当我填写数量与单价，那么自动计算小计、税费与总计。
- 给定填写完成，当我点击导出，那么生成 PDF 并保留在历史记录里。
- 给定单价为空，当我点击导出，那么阻止提交并指出缺失字段。
```

**验收标准写得越具体，返工越少**。如果一条验收标准无法写成一个自动化测试，说明它还太模糊。

## 二、范围控制：MVP 与不做清单

| 类别 | 内容 | 说明 |
| --- | --- | --- |
| 必须有（MVP） | 没有它产品不成立 | 例如：创建报价单、导出 PDF、查看历史 |
| 应该有 | 影响体验但可延后 | 例如：模板管理、批量操作 |
| 可以有 | 锦上添花 | 例如：深色模式、快捷键 |
| **不做** | 明确排除 | 例如：多币种、团队协作、移动 App |

**「不做清单」必须写下来并对外公布**。它是你抵御范围蔓延的唯一武器：

```text
本项目不做：
- 在线支付（与核心价值无关）
- 多语言（目标用户仅中文）
- 移动端原生应用（响应式 Web 已足够）
- 团队协作与权限体系（个人工具定位）
```

## 三、技术选型：用 ADR 记录决策

每条选型写一份简短记录（Architecture Decision Record）：

```markdown
## ADR-001 为什么选 PostgreSQL 而不是 MongoDB

- 背景：报价单有明确的行项目结构，且需要按客户、时间做聚合统计。
- 决策：使用 PostgreSQL。
- 理由：数据关系明确，聚合查询多；事务保证报价单与行项目一致；JSONB 可存放模板等半结构化配置。
- 代价：需要处理 schema 迁移；横向扩展不如文档数据库灵活。
- 替代方案：MongoDB（放弃，聚合与事务较复杂）；SQLite（放弃，多用户并发与备份不便）。
```

| 决策对象 | 需要评估的维度 |
| --- | --- |
| 数据库 | 数据形状、一致性要求、查询模式、运维成本 |
| 前端框架 | 团队熟悉度、生态、SEO 需求、渲染方式 |
| 认证方案 | 客户端类型、是否需要即时撤销、跨域要求 |
| 部署方式 | 预算、流量规模、是否需要自建数据库 |
| 状态管理 | 状态分类（服务端／共享／局部）、团队规模 |

**选型三条原则**：
1. 优先选团队已掌握的技术（学习成本是最贵的成本）。
2. 优先选生态活跃、文档齐全的技术（遇到问题能找到答案）。
3. 优先选能卸载责任的方案（托管服务好过自建，除非有明确理由）。

## 四、数据模型先行

```text
users(id, email, name, created_at)
templates(id, user_id, name, config jsonb, created_at)
quotes(id, user_id, client_name, currency, status, subtotal, tax, total, created_at)
quote_items(id, quote_id, description, qty, unit_price, amount)
audit_logs(id, user_id, action, target_type, target_id, payload jsonb, created_at)
```

**先定表再写接口**：接口形状由数据形状决定。表定错，接口和界面都要返工。

**金额用什么存**：用整数分或 `numeric(12,2)`，绝不用浮点。状态字段用受约束的枚举（`check` 或应用层联合类型）。

## 五、接口与前端骨架

```text
POST   /api/v1/quotes              创建报价单（草稿）
PATCH  /api/v1/quotes/:id          更新（含行项目）
POST   /api/v1/quotes/:id/issue    定稿（此后不可改金额）
GET    /api/v1/quotes/:id/export   导出 PDF
GET    /api/v1/quotes?status=&cursor=&limit=
```

前端页面骨架：登录 → 列表（筛选／分页）→ 编辑（表单 + 行项目）→ 预览导出 → 模板设置。

**先把这些路由和空页面做出来**：能看到全貌，心里就有进度感。

## 六、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 做了两个月还在改需求 | 没有「不做清单」 | 冻结范围，新增需求进下一个版本 |
| 界面改一次要改十处 | 数据模型反复变 | 先定模型再做界面 |
| 选了个不熟的技术，两周没跑通 | 学习成本被低估 | 换回熟悉的方案，或先做技术预研 |
| 功能都做了但没有一个能用 | 没有端到端验收 | 每个功能都要能独立演示 |
| 金额算错 | 用了浮点数 | 整数分或 decimal |
