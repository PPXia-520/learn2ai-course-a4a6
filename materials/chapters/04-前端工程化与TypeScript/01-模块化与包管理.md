# 01 · 模块化与包管理

## 一、为什么需要模块化

一个文件写 3000 行代码会带来三个问题：命名冲突、依赖关系看不见、无法按需加载。模块化把代码按职责切开，通过明确的导入导出建立依赖图，让「谁依赖谁」变得可追踪、可检查、可测试。

## 二、ESM 与 CommonJS

| 维度 | ESM（`import`/`export`） | CommonJS（`require`/`module.exports`） |
| --- | --- | --- |
| 标准 | ECMAScript 官方标准 | Node 早期事实标准 |
| 加载时机 | 静态分析，编译期确定依赖 | 运行时执行到才加载 |
| 能否摇树优化 | 能（静态结构可分析） | 通常不能 |
| 顶层 `await` | 支持 | 不支持 |
| 浏览器原生支持 | 支持（`type=module`） | 不支持 |
| 适用 | 新项目一律首选 | 维护老项目时兼容 |

```js
// ESM：命名导出 + 默认导出
export const add = (a, b) => a + b;
export default function sum(list) { return list.reduce(add, 0); }

// 导入
import sum, { add } from './math.js';
```

```js
// CommonJS
const path = require('node:path');
module.exports = { join: path.join };
```

**互操作注意**：ESM 导入 CJS 时通常只能拿到默认导出；从 ESM 项目引用老包，优先找它有没有提供 ESM 入口。

## 三、依赖分类与版本

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| `dependencies` | 运行时必需 | `react`、`zod` |
| `devDependencies` | 只在开发／构建期需要 | `typescript`、`vite`、`vitest` |
| `peerDependencies` | 要求宿主项目提供 | 组件库声明 `react` |
| `optionalDependencies` | 可选，失败不阻塞安装 | 平台相关的二进制包 |

**语义化版本（SemVer）**：`主版本.次版本.修订号`

| 写法 | 允许范围 | 何时用 |
| --- | --- | --- |
| `1.2.3` | 精确锁定 | 关键依赖需要完全可复现 |
| `^1.2.3` | 允许 `1.x` 升级 | 默认，兼容性较好 |
| `~1.2.3` | 只允许 `1.2.x` | 次版本也可能破坏时 |
| `*` / `latest` | 任意 | **禁止**在生产项目使用 |

**锁文件**（`package-lock.json`／`pnpm-lock.yaml`）记录完整的依赖树与哈希。它必须提交到仓库——否则「我这里能跑」将永远无法复现。

## 四、包管理器选择

| 工具 | 特点 | 适用 |
| --- | --- | --- |
| npm | 随 Node 自带，生态最广 | 通用、教学、CI 默认 |
| pnpm | 硬链接共享，磁盘占用小、安装快 | 多项目、Monorepo |
| yarn | 早期并行安装优势，现代版有 PnP | 已有 yarn 项目 |

```bash
npm ci                 # 严格按锁文件安装，CI 环境专用（比 npm install 更快更稳）
npm outdated           # 看哪些依赖有新版本
npm audit              # 检查已知漏洞
npm ls <包名>           # 谁把我引进来的？
```

## 五、Monorepo：多包同仓

适用信号：多个应用需要共享组件库、工具函数或类型定义，且发布节奏相近。

```
repo/
  apps/
    web/           # 面向用户的应用
    admin/         # 后台应用
  packages/
    ui/            # 共享组件库
    shared/        # 类型与工具函数
  pnpm-workspace.yaml
```

| 优点 | 代价 |
| --- | --- |
| 共享代码零发布成本 | 构建与 CI 需要增量策略 |
| 类型与规范统一 | 权限与版本管理更复杂 |
| 一次改动可跨包验证 | 仓库体积增长快 |

**建议**：课程阶段先用单包仓库，第 12 章再按需引入 workspace。

## 六、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 删掉 `node_modules` 重装后行为变了 | 没提交锁文件 | 提交锁文件，CI 用 `npm ci` |
| 循环依赖导致某处是 `undefined` | 模块互相 import | 抽公共模块，或把依赖改成参数传入 |
| 改了依赖但没生效 | 构建缓存 | 清缓存重启，检查是否有多个版本共存 |
| `Cannot use import statement outside a module` | Node 未按 ESM 解析 | 在 `package.json` 设 `type: module` 或改用 `.mjs` |
| 安装体积异常大 | 依赖了体积失控的包 | `npm ls` 追根因，或用 `bundlephobia` 评估替代 |

## 七、动手练习

1. 建一个 ESM 项目，写三个模块并画出依赖关系图。
2. 用 `npm ls` 找出某个间接依赖的来源，并解释它为什么被引入。
3. 把某个依赖从 `^` 改成精确版本，观察锁文件变化。
4. 故意制造一个循环依赖，复现 `undefined` 问题并修复。
