# 02 · 构建工具与工程配置

## 一、构建工具到底做了什么

```
TypeScript / JSX ──转译──▶ JS ──依赖分析──▶ 打包(可选) ──压缩──▶ 产物
                                                                  ├─ 代码分割：按路由/组件拆成多个 chunk
                                                                  ├─ 资源处理：CSS、图片、字体指纹
                                                                  └─ HMR：开发态只替换改动的模块
```

见 `assets/build-pipeline.svg`。选择构建工具时看清三件事：**开发启动速度**、**生产产物质量**、**生态与配置成本**。

| 工具 | 定位 | 何时选 |
| --- | --- | --- |
| Vite | 开发用原生 ESM，生产用 Rollup | 新项目默认选择 |
| Rollup | 库打包，产物干净 | 发布 npm 库 |
| webpack | 生态成熟、插件极多 | 维护老项目、特殊定制需求 |
| esbuild / SWC | 极快的转译器 | 作为其他工具的内部引擎 |

## 三、Vite 关键配置

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import { fileURLToPath, URL } from 'node:url';

export default defineConfig(({ mode }) => ({
  plugins: [react()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
  server: {
    port: 5173,
    open: true,
    proxy: {
      '/api': { target: 'http://localhost:3000', changeOrigin: true },
    },
  },
  build: {
    sourcemap: mode !== 'production',
    rollupOptions: {
      output: {
        manualChunks: { vendor: ['react', 'react-dom'] },
      },
    },
  },
}));
```

要点解释：

| 配置 | 作用 | 为什么需要 |
| --- | --- | --- |
| `resolve.alias` | 用 `@/` 指向 `src` | 避免 `../../../` 地狱 |
| `server.proxy` | 开发期把 `/api` 转发到后端 | 避免开发时跨域问题 |
| `build.sourcemap` | 保留源码映射 | 线上报错能定位到源文件 |
| `manualChunks` | 把第三方库拆包 | 让业务代码变更不必让用户重下依赖 |

## 四、环境变量

```bash
# .env.development
VITE_API_BASE=/api
VITE_FEATURE_CHAT=true
```

```ts
const base = import.meta.env.VITE_API_BASE;
const isChatOn = import.meta.env.VITE_FEATURE_CHAT === 'true';
```

| 规则 | 说明 |
| --- | --- |
| 只有 `VITE_` 前缀会暴露给客户端 | 防止误把服务端密钥打进产物 |
| 客户端变量会被打进产物 | **绝不**放密钥、令牌、数据库连接串 |
| 类型提示 | 在 `src/vite-env.d.ts` 中声明 `ImportMetaEnv` 接口 |
| `.env.example` 提交、`.env*` 忽略 | 让新人知道要配什么，又不泄密 |

## 五、npm scripts：把命令固化下来

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc --noEmit && vite build",
    "preview": "vite preview",
    "typecheck": "tsc --noEmit",
    "lint": "eslint . --max-warnings=0",
    "format": "prettier --write .",
    "test": "vitest run"
  }
}
```

**原则**：任何人 checkout 后只跑 `npm install` + `npm run dev` 就能开始工作；CI 只跑这些脚本，不写额外命令。

## 六、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 生产构建后白屏 | 部署在子路径下，资源路径是绝对路径 | 设 `base: '/子路径/'` |
| 环境变量是 `undefined` | 变量名缺少 `VITE_` 前缀 | 改名并重启开发服务器 |
| 改了 `.env` 没生效 | 环境变量在启动时注入 | 重启 `npm run dev` |
| 依赖的包只有 CJS，导入报错 | 无 ESM 入口 | 用 `optimizeDeps.include` 预构建 |
| 类型检查过了但运行报错 | 用了 `any`／类型断言绕过 | 用运行时校验（如 zod）兜底 |
| CI 本地结果不一致 | Node 版本不同 | 用 `.nvmrc` 与 CI 统一版本 |

## 七、动手练习

1. 配好 `@` 别名，并把 3 处深层相对路径改为别名引用。
2. 配好 `/api` 代理，用本地 mock 服务验证请求被转发。
3. 增加一个 `VITE_APP_TITLE` 变量，在页面上显示它，并把它加入 `.env.example`。
4. 给构建产物加 `manualChunks`，对比配置前后各 chunk 的体积。
