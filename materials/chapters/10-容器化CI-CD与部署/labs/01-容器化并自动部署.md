# Lab 10 · 容器化并自动部署

## 目标
把前面章节做出来的全栈应用容器化，接入流水线，部署到公网可访问，并成功完成一次回滚。

## 任务一 · 镜像构建
1. 写多阶段 Dockerfile：依赖层 → 构建层 → 运行层。
2. 加 `.dockerignore`，排除 `node_modules`、`dist`、`.git`、`.env*`、`coverage`。
3. 非 root 用户运行，配置 `HEALTHCHECK`。
4. 记录：镜像体积、构建耗时、`docker history` 的前几层。

## 任务二 · 本地编排
1. 用 Compose 起「应用 + PostgreSQL + Redis」。
2. 应用通过服务名连接数据库（不是 `localhost`）。
3. 数据库与缓存都挂命名卷，验证 `docker compose down` 后再 `up` 数据仍在。
4. 验证 `depends_on` + `healthcheck` 生效：数据库没就绪时应用不会先崩。

## 任务三 · 流水线
1. 写 CI：`npm ci` → typecheck → lint → test → build，任一步失败即终止。
2. 加发布任务：构建镜像并推送到镜像仓库，标签为 `sha-<前 7 位>` 与 `latest`。
3. 加部署任务：使用 `environment: production`（配置人工审批）。
4. 截图或导出一次「校验失败被拦住」与一次「全绿自动发布」的流水线记录。

## 任务四 · 上线与回滚
1. 部署到公网可访问的环境（云平台或隧道工具均可），记录访问地址。
2. 记录当前版本号（镜像 tag）与部署时间。
3. 故意引入一个可观察的缺陷（如把首页标题改错），走完整流程发布。
4. 用同一套命令部署上一个 sha，完成回滚，并记录：
   - 从决定回滚到恢复可用的耗时；
   - 回滚期间用户看到什么；
   - 数据库结构是否需要特殊处理。

## 任务五 · 观测与告警
1. 应用输出结构化 JSON 日志，含 requestId、路径、状态码、耗时。
2. 加 `/health` 接口，返回进程与依赖（数据库、缓存）的状态。
3. 配置一条告警规则（错误率 > 5% 或健康检查失败），并演示触发。

## 验收清单
- [ ] 镜像可 `docker run` 启动并响应 `/health`；镜像中不含 devDependencies。
- [ ] Compose 一条命令起全套；数据卷在重启后保留。
- [ ] 流水线四步串联，附失败拦截与成功发布两条记录。
- [ ] 镜像标签使用 commit sha，可据此回滚。
- [ ] 公网地址可访问，附访问截图。
- [ ] 回滚记录含耗时、用户影响与数据库处理说明。
- [ ] 日志可凭 requestId 串起一次请求的全部记录。
- [ ] 告警有一次真实触发记录。

## 加分项
1. 用金丝雀方式发布：先 5% 流量，观察 10 分钟无异常再全量。
2. 加数据库迁移的自动执行与失败回滚策略。
3. 把部署耗时从分钟级优化到 30 秒内，给出优化手段与数据。
4. 用 IaC 描述部署环境，做到「一条命令重建整套环境」。
