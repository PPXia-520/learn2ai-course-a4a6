# 03 · 前端性能与测试

## 一、先测量，再优化

性能优化的顺序永远是：**测量 → 定位 → 优化 → 复测**。凭感觉优化通常会把代码改复杂而没有收益。

| 工具 | 看什么 |
| --- | --- |
| React DevTools Profiler | 哪些组件渲染了、各花了多久、为什么渲染 |
| 浏览器 Performance 面板 | 长任务、布局抖动、帧率 |
| Lighthouse | 首屏指标、体积、无障碍 |
| 打包分析器 | 哪个包占了体积 |

## 二、重渲染的三种常见原因

1. **父组件重渲染**带动子组件一起渲染（未 `memo`）。
2. **引用不稳定**：每次渲染都新建的对象／函数作为 props，让 `memo` 失效。
3. **状态位置过高**：一个局部状态放在全局，改一次牵动整棵树。

```jsx
const Item = memo(function Item({ todo, onToggle }) {
  return <li onClick={() => onToggle(todo.id)}>{todo.title}</li>;
});

function List({ todos }) {
  const [keyword, setKeyword] = useState('');
  const toggle = useCallback((id) => { /* ... */ }, []);   // 引用稳定，Item 才不会白渲染
  const visible = useMemo(
    () => todos.filter(t => t.title.includes(keyword)),
    [todos, keyword],
  );
  return (
    <>
      <input value={keyword} onChange={e => setKeyword(e.target.value)} />
      <ul>{visible.map(t => <Item key={t.id} todo={t} onToggle={toggle} />)}</ul>
    </>
  );
}
```

**注意**：`memo` + `useCallback` 不是越多越好。当组件本身很轻，包裹的开销可能超过收益。

## 三、加载性能

| 手段 | 做法 | 收益 |
| --- | --- | --- |
| 路由级代码分割 | 每个页面单独 chunk，按需加载 | 首屏 JS 明显变小 |
| 组件懒加载 | 重组件（编辑器、图表）用 `lazy` + `Suspense` | 不阻塞首屏 |
| 依赖瘦身 | 用体积小的替代库，或用原生 API | 直接减少下载量 |
| 图片优化 | 现代格式、`loading=lazy`、明确宽高 | 减少布局偏移 |
| 预加载关键资源 | `preload` / `prefetch` | 提前开始下载 |

```jsx
const Chart = lazy(() => import('./Chart'));

<Suspense fallback={<Skeleton />}>
  <Chart data={data} />
</Suspense>
```

## 四、组件测试：像用户一样测试

原则：**测试行为，不测实现细节**。只要用户看到的结果不变，重构就不该让测试失败。

```jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('加载成功后展示任务列表', async () => {
  vi.spyOn(global, 'fetch').mockResolvedValueOnce({
    ok: true, json: async () => [{ id: '1', title: '写作业' }],
  });

  render(<TodoList />);

  expect(screen.getByText('加载中')).toBeInTheDocument();
  expect(await screen.findByText('写作业')).toBeInTheDocument();
});

test('请求失败时展示错误提示', async () => {
  vi.spyOn(global, 'fetch').mockResolvedValueOnce({ ok: false, status: 500 });
  render(<TodoList />);
  expect(await screen.findByRole('alert')).toHaveTextContent('500');
});

test('点击可以标记完成', async () => {
  render(<TodoItem todo={{ id: '1', title: '写作业', done: false }} onToggle={() => {}} />);
  await userEvent.click(screen.getByRole('checkbox'));
});
```

| 查询优先级 | 用法 | 说明 |
| --- | --- | --- |
| 角色查询 | `getByRole('button', { name: '提交' })` | 最推荐，同时验证无障碍 |
| 文本查询 | `getByText('加载中')` | 直观 |
| 测试 id | `getByTestId('chart')` | 最后手段 |

## 五、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 加了 `memo` 没效果 | props 引用每次都变 | 用 `useCallback`／`useMemo` 稳定引用 |
| 首屏仍然很大 | 依赖全打进主 chunk | 配 `manualChunks` + 路由懒加载 |
| 测试老是超时 | 断言写在同步代码里 | 用 `findBy*` 等异步查询 |
| 测试改个类名就挂 | 断言了实现细节 | 改用角色／文本查询 |
| 图省事断言快照 | 快照无人审阅 | 只对稳定的小结构用，并人工确认 |

## 六、动手练习

1. 用 Profiler 找出一次不必要重渲染并修复，记录优化前后耗时。
2. 给一个重页面加路由懒加载，对比构建产物体积。
3. 为列表、详情、表单各写一个测试，覆盖成功与失败路径。
4. 把某个测试从 `getByTestId` 改为角色查询，并说明为什么更好。
