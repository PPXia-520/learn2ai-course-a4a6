# 01 · 认证与授权机制

## 一、两个必须分清的概念

| 概念 | 回答的问题 | 失败时的状态码 | 例子 |
| --- | --- | --- | --- |
| 认证 Authentication | 你是谁 | 401 | 未登录、令牌过期 |
| 授权 Authorization | 你能做什么 | 403 | 普通用户访问管理接口 |

## 二、会话方案对比

| 方案 | 状态存放 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 服务端 Session | 服务端存储，Cookie 存 sessionId | 可即时撤销、实现简单 | 需要共享存储（多实例） | 传统 Web 应用、后台系统 |
| JWT（无状态） | 令牌自带信息，客户端保存 | 无需服务端存储、易横向扩展 | 难以即时撤销、体积较大 | 移动端、跨域 API |
| 混合方案 | 短效 access token + 服务端存的 refresh token | 兼顾性能与可控性 | 实现稍复杂 | 生产环境推荐 |

见 `assets/auth-flow.svg`。

## 三、Cookie 安全属性

```http
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
```

| 属性 | 作用 | 不设置的后果 |
| --- | --- | --- |
| `HttpOnly` | 禁止 JS 读取 | XSS 可直接窃取会话 |
| `Secure` | 只在 HTTPS 发送 | 明文网络下被窃听 |
| `SameSite=Lax/Strict` | 限制跨站发送 | CSRF 风险升高 |
| `Max-Age`／`Expires` | 过期时间 | 会话永久有效 |
| `Path`／`Domain` | 作用范围 | 泄漏到不必要的路径 |

## 四、密码存储

```ts
import bcrypt from 'bcrypt';

// 注册：只存哈希，永远不存明文、不用可逆加密
const hash = await bcrypt.hash(password, 12);          // cost 12，按机器性能调整
await users.create({ email, passwordHash: hash });

// 登录：用恒定时间比较，避免时序攻击
const user = await users.findByEmail(email);
const ok = user ? await bcrypt.compare(password, user.passwordHash) : false;
if (!ok) throw new AppError('邮箱或密码错误', 401, 'INVALID_CREDENTIALS');
```

三条硬规则：

1. **错误信息不区分「邮箱不存在」与「密码错误」**，避免枚举用户。
2. **登录接口必须限流**（按 IP 与账号），并加失败次数锁定。
3. **不要自己实现哈希算法**，用成熟的库；不要用 MD5／SHA1。

## 五、令牌签发与校验

```ts
import jwt from 'jsonwebtoken';

const signAccess = (user) => jwt.sign(
  { sub: user.id, role: user.role },
  process.env.JWT_SECRET,
  { expiresIn: '15m', issuer: 'api.example.com', audience: 'web' },
);

// 校验中间件
export const authenticate = (req, res, next) => {
  const header = req.headers.authorization ?? '';
  const [scheme, token] = header.split(' ');
  if (scheme !== 'Bearer' || !token) return next(new AppError('未提供凭证', 401, 'UNAUTHENTICATED'));

  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET, {
      issuer: 'api.example.com', audience: 'web',
    });
    req.user = { id: payload.sub, role: payload.role };
    next();
  } catch (err) {
    const code = err.name === 'TokenExpiredError' ? 'TOKEN_EXPIRED' : 'INVALID_TOKEN';
    next(new AppError('凭证无效或已过期', 401, code));
  }
};
```

**JWT 的三条注意事项**：
1. 令牌内容**能被任何人读**（只是 Base64，不是加密），不要放敏感信息。
2. 有效期要短（access token 15 分钟级），用 refresh token 换新令牌。
3. 退出登录时若无法撤销，必须让 refresh token 失效（服务端存白名单或版本号）。

## 六、授权：从简单角色到细粒度

```ts
// 1. 角色校验
const requireRole = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) return next(new AppError('权限不足', 403, 'FORBIDDEN'));
  next();
};
router.delete('/posts/:id', authenticate, requireRole('admin'), handler);

// 2. 资源归属校验——最容易被忽略、也最常出漏洞的一类
async function updatePost(req, res, next) {
  const post = await postService.findById(req.params.id);
  if (!post) return next(notFound('文章'));

  const canEdit = post.authorId === req.user.id || req.user.role === 'admin';
  if (!canEdit) return next(new AppError('无权修改他人文章', 403, 'FORBIDDEN'));

  next();
}
```

**水平越权（IDOR）**：改了 URL 里的 id 就能访问别人的数据。防御方式是**每次访问都校验归属**，而不是只在列表接口过滤。返回 404 而不是 403 也能减少信息泄露。

| 模型 | 说明 | 适用 |
| --- | --- | --- |
| RBAC | 角色决定权限 | 大多数后台系统 |
| ABAC | 按属性（部门、归属、时间）判断 | 复杂组织与数据权限 |
| 权限位 | 每个资源存一组操作权限 | 协作类产品（如文档共享） |

## 七、刷新与撤销

```text
登录 → 签发 access（15 分钟）+ refresh（7 天，服务端存 jti）
access 过期 → 用 refresh 换新 access（refresh 轮换，旧的作废）
退出登录 → 服务端删除 refresh 记录 → 后续换取失败
```

**关键点**：refresh token 必须轮换（每次换新并作废旧的），否则一旦泄露可长期使用。

## 八、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 令牌放在 localStorage 被脚本读走 | XSS 后可窃取 | 用 `HttpOnly` Cookie 或严格 CSP |
| 改 id 能看别人数据 | 只在前端做判断 | 服务端每次校验归属 |
| 退出登录后令牌仍可用 | JWT 无状态、无法撤销 | 缩短有效期 + refresh 白名单 |
| 登录接口被暴力破解 | 无限流 | 按 IP 与账号限流、失败锁定 |
| 生产环境用了默认密钥 | 未校验必需配置 | 启动时强校验 `JWT_SECRET` |
| 日志里记录了密码 | 直接打印整个请求体 | 日志字段白名单，脱敏敏感字段 |
