# 02 · 集成测试与 E2E 测试

## 一、集成测试：验证「拼起来能用」

集成测试关注模块之间的协作契约：HTTP 层能否正确解析、SQL 是否真的写进库、事务边界是否正确、错误是否被正确映射成状态码。

```ts
// 用真实 HTTP 栈请求应用，只替换数据库为独立测试库
import request from 'supertest';
import { app } from '../src/app.js';

describe('POST /api/v1/tasks', () => {
  it('缺少标题返回 422 且指出字段', async () => {
    const res = await request(app).post('/api/v1/tasks').send({});
    expect(res.status).toBe(422);
    expect(res.body.error.code).toBe('VALIDATION_FAILED');
    expect(res.body.error.details[0].field).toBe('title');
  });

  it('创建成功返回 201 与 Location 头', async () => {
    const res = await request(app)
      .post('/api/v1/tasks')
      .set('Authorization', `Bearer ${token}`)
      .send({ title: '写周报' });
    expect(res.status).toBe(201);
    expect(res.headers.location).toMatch(/^\/api\/v1\/tasks\/\d+$/);
  });

  it('重复创建同名任务返回 409', async () => { /* ... */ });
  it('访问他人任务返回 403 或 404', async () => { /* ... */ });
});
```

### 数据库隔离的三种做法

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 事务回滚 | 每个测试在事务中运行，结束回滚 | 快、互不干扰 | 无法测事务本身的行为 |
| 独立 schema | 每个测试文件建独立 schema | 隔离彻底 | 建表开销 |
| 容器实例 | 用 Testcontainers 起临时数据库 | 最接近生产 | 启动稍慢 |

**必备原则**：测试库与开发库分离，运行测试时绝不连接生产库。用环境变量显式指定，并在启动时校验数据库名（例如必须包含 `_test`）。

## 二、E2E 测试：从用户视角走一遍

```ts
import { test, expect } from '@playwright/test';

test('登录后能创建任务并看到它', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('邮箱').fill('demo@example.com');
  await page.getByLabel('密码').fill('Passw0rd!');
  await page.getByRole('button', { name: '登录' }).click();

  await expect(page.getByRole('heading', { name: '我的任务' })).toBeVisible();

  await page.getByLabel('新任务').fill('写测试');
  await page.getByRole('button', { name: '添加' }).click();

  await expect(page.getByRole('listitem').filter({ hasText: '写测试' })).toBeVisible();
});
```

| 建议 | 原因 |
| --- | --- |
| 用角色／标签查询 | 与无障碍属性一致，界面重构不易失效 |
| 不写固定等待 `sleep` | 用「等待某元素出现」的自动重试断言 |
| 每个用例自带数据准备与清理 | 保证可重复运行 |
| 只覆盖关键路径 | E2E 慢且贵，抓住主干即可 |
| 失败时保留截图与视频 | 事后排查的唯一线索 |

## 三、抖动（Flaky）测试治理

| 抖动原因 | 表现 | 处理 |
| --- | --- | --- |
| 固定等待 | 本地过、CI 挂 | 改为显式等待条件 |
| 测试数据冲突 | 并行时唯一键冲突 | 数据加随机后缀，或用独立库 |
| 时间与时区 | 跨天运行时失败 | 固定时钟与时区 |
| 顺序依赖 | 单独跑通过，全量跑失败 | 每个用例自建数据 |
| 资源竞争 | 端口占用、并发写同一行 | 随机端口、数据隔离 |

**处理原则**：抖动测试要么立刻修，要么标记隔离并建单跟踪——**不能放任它长期红着**，那会让所有人开始忽略红灯。

## 四、测试要与 CI 结合

```yaml
# 分层执行：快反馈在前，慢验证在后
jobs:
  verify:
    steps:
      - run: npm ci
      - run: npm run typecheck
      - run: npm run lint
      - run: npm run test -- --coverage       # 单元 + 集成
      - run: npm run build
  e2e:
    needs: verify
    steps:
      - run: npx playwright install --with-deps chromium
      - run: npm run test:e2e
```

原则：**前一步不通过就不进入下一步**，让失败尽可能早、尽可能便宜地暴露。

## 五、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 测试写进了生产库 | 环境变量配置错误 | 强制校验库名后缀，CI 用独立实例 |
| 集成测试互相污染 | 共用数据未清理 | 每个用例独立数据 + 事务回滚 |
| E2E 在 CI 上总超时 | 依赖本地有头浏览器或网络 | 无头模式、依赖内网 mock |
| 测试跑得很慢 | E2E 过多、未并行 | 下沉到单元／集成层，开启并行 |
| 只测 happy path | 忽略错误分支 | 每个接口至少一个失败用例 |

## 六、动手练习

1. 为三个接口各写「成功 + 一个失败」两个集成测试。
2. 用事务回滚实现测试数据隔离，并验证用例可乱序执行。
3. 写一个 E2E：登录 → 创建 → 编辑 → 删除，全程无固定等待。
4. 故意制造一个抖动测试，用显式等待修复它。
