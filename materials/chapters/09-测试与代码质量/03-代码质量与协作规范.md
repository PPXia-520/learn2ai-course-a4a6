# 03 · 代码质量与协作规范

## 一、质量门槛的四道闸门

```
编辑器保存 → 本地提交钩子 → CI 流水线 → 代码评审
格式化       lint 暂存文件   typecheck+test+build  人的判断
```

自动化处理「机器能判断的」，人只处理「需要权衡的」。

## 二、静态检查与格式化

```js
// eslint.config.js（扁平配置）
export default [
  { ignores: ['dist/**', 'coverage/**'] },
  {
    files: ['**/*.{ts,tsx,js}'],
    rules: {
      'no-console': ['warn', { allow: ['warn', 'error'] }],
      'no-unused-vars': 'off',
      '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }],
      '@typescript-eslint/no-explicit-any': 'error',
      'eqeqeq': ['error', 'always'],
      'prefer-const': 'error',
    },
  },
];
```

| 工具 | 职责 | 关键设置 |
| --- | --- | --- |
| Prettier | 纯格式化，不做逻辑判断 | 与编辑器保存联动 |
| ESLint | 发现潜在错误与坏味道 | CI 中 `--max-warnings=0` |
| TypeScript | 类型正确性 | `strict: true` |
| EditorConfig | 缩进／换行统一 | 跨编辑器一致 |

**纪律**：格式化与静态检查都不该在代码评审里讨论——机器能解决的争论不叫技术讨论。

## 三、提交钩子与提交规范

```json
{
  "scripts": {
    "prepare": "husky",
    "lint-staged": "lint-staged"
  },
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix --max-warnings=0", "prettier --write"],
    "*.{json,md,css}": ["prettier --write"]
  }
}
```

| 规范 | 内容 |
| --- | --- |
| Conventional Commits | `feat` / `fix` / `docs` / `refactor` / `test` / `chore` |
| 一次提交一件事 | 便于回滚与定位 |
| 提交信息写「为什么」 | diff 已经说明了「做了什么」 |
| 关联任务编号 | `feat: 支持手机号登录 (#142)` |

## 四、CI 流水线的质量门槛

```yaml
name: verify
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run typecheck
      - run: npm run lint
      - run: npm run test -- --coverage
      - run: npm run build
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: reports, path: coverage/ }
```

**必须满足**：流水线失败禁止合并；主干始终可部署；分支保护要求至少一人评审。

## 五、代码评审：给意见与收意见

### 评审者：看什么、按什么顺序

| 优先级 | 关注点 | 例子 |
| --- | --- | --- |
| 1 | 正确性与边界 | 空数组、并发、错误分支是否处理 |
| 2 | 安全 | 输入是否校验、是否越权、是否泄漏敏感字段 |
| 3 | 可维护性 | 命名、函数长度、重复代码、耦合 |
| 4 | 性能 | N+1、循环里的 IO、不必要的重渲染 |
| 5 | 风格 | 交给工具，不占评审时间 |

### 反馈的语气与结构

| 差的说法 | 好的说法 |
| --- | --- |
| 「这样写不对」 | 「这里并发时会丢失更新，建议加行锁，示例：……」 |
| 「重写吧」 | 「如果把这段抽成 `calculateTotal`，两个调用方都能复用，你看是否合适？」 |
| 「为什么不加测试？」 | 「这个分支容易回归，能否补一个用例？」 |

**提问式反馈优于命令式**：既表达观点，也留出对方解释的余地。

### 收到意见时

1. 先假设对方是对的，复现一次再说「我不同意」。
2. 用技术理由回应，不用「一直这么写的」。
3. 达成一致后更新代码，并回复说明改动在哪。
4. 分歧无法收敛时，升级给更有经验的人，不要拖。

## 六、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| CI 红灯长期挂着 | 无人负责 | 红灯优先于新需求 |
| 评审变成风格争吵 | 未接入工具 | 用 Prettier + ESLint 消除争议 |
| 提交信息全是 `update` | 无规范 | 加提交信息校验 |
| 评审 1000 行的大 PR | 分支存活过久 | 拆小 PR，早提交早评审 |
| 忽略警告 | `--max-warnings` 未设 | CI 中设为 0 |

## 七、动手练习

1. 给工程接入 Prettier + ESLint + husky，制造一次提交失败再修复。
2. 写一条 GitHub Actions 流水线，串联四道检查并上传覆盖率报告。
3. 找一段你自己写的代码做自评，按上面的优先级顺序写 5 条意见。
4. 找一个开源项目的 PR，读三条评审意见并复述它的技术理由。
