# 01 · 测试金字塔与单元测试

## 一、测试金字塔

```
        ▲  少、慢、贵
      E2E 端到端        覆盖关键用户流程，如「下单成功」
    ───────────────
    集成测试            接口 + 数据库 + 外部依赖的协作
  ───────────────────
  单元测试              纯函数、业务规则、边界条件
        ▼  多、快、便宜
```

| 层级 | 测什么 | 数量级 | 运行时间 | 失败时的信息量 |
| --- | --- | --- | --- | --- |
| 单元 | 单个函数／模块的逻辑分支 | 最多 | 毫秒级 | 精确到函数 |
| 集成 | 模块协作、SQL、HTTP 契约 | 中等 | 秒级 | 定位到模块 |
| E2E | 真实浏览器的完整流程 | 最少 | 分钟级 | 只知道流程坏了 |

**不要倒金字塔**：大量 E2E 会带来漫长的流水线和频繁的抖动，团队最终会开始忽略失败。

## 二、一个合格的单元测试

```ts
// 被测对象：纯函数，易测
export function calculateDiscount(items: OrderItem[], coupon?: Coupon): number {
  const total = items.reduce((sum, i) => sum + i.price * i.qty, 0);
  if (!coupon) return 0;
  if (coupon.expiresAt.getTime() < Date.now()) return 0;
  if (total < coupon.minAmount) return 0;
  return Math.min(total * coupon.rate, coupon.maxDiscount ?? Infinity);
}
```

```ts
describe('calculateDiscount', () => {
  const items = [{ price: 100, qty: 2 }];

  it('无优惠券时不打折', () => {
    expect(calculateDiscount(items)).toBe(0);
  });

  it('满足门槛时按比例打折', () => {
    expect(calculateDiscount(items, { rate: 0.1, minAmount: 100, expiresAt: future })).toBe(20);
  });

  it('未达门槛时不打折', () => {          // 边界：刚好差 1 分
    expect(calculateDiscount(items, { rate: 0.1, minAmount: 200, expiresAt: future })).toBe(0);
  });

  it('过期优惠券不生效', () => {
    expect(calculateDiscount(items, { rate: 0.1, minAmount: 100, expiresAt: past })).toBe(0);
  });

  it('折扣不超过上限', () => {
    expect(calculateDiscount(items, { rate: 0.5, minAmount: 0, maxDiscount: 50, expiresAt: future })).toBe(50);
  });
});
```

结构遵循 **AAA**：Arrange（准备）→ Act（执行）→ Assert（断言）。一个测试只验证一件事。

## 三、测试命名与断言

| 反例 | 正例 |
| --- | --- |
| `test('test1')` | `it('未达门槛时不打折')` |
| `it('works')` | `it('过期优惠券不生效')` |
| `expect(x).toBeTruthy()` | `expect(result).toBe(20)` |
| 一个测试里断言 8 件事 | 拆成多个测试 |

**命名公式**：`在什么条件下 → 做什么 → 期望什么`。测试名应该能当作需求文档读。

## 四、Mock：只隔离外部世界

```ts
// 只 mock 边界：网络、时间、随机、文件系统
vi.mock('./mailer', () => ({ send: vi.fn().mockResolvedValue(undefined) }));

// 时间要可控，否则测试在凌晨会失败
vi.useFakeTimers();
vi.setSystemTime(new Date('2026-10-07T00:00:00Z'));
```

| 该 mock | 不该 mock |
| --- | --- |
| 网络请求、邮件、支付网关 | 被测函数内部的纯函数 |
| 当前时间、随机数 | 数据结构与工具函数 |
| 文件系统、第三方 SDK | 你自己写的领域逻辑 |

**过度 mock 的信号**：测试里 mock 的数量超过断言的 2 倍，说明被测单元设计过于依赖外部。

## 五、该测什么：优先级清单

1. **业务规则分支**：金额计算、状态机流转、权限判定。
2. **边界条件**：0、空数组、最大值、刚好相等、差一点。
3. **错误路径**：非法输入、依赖失败、超时。
4. **曾经出过 bug 的地方**：每修一个 bug 补一个测试。
5. **不测**：框架自身行为、纯展示组件、一次性脚本。

## 六、覆盖率怎么用

覆盖率是**发现盲区的工具，不是目标**。80% 的行覆盖配上「每行都调用过但没断言」等于零收益。看两类数据更有价值：

- **未覆盖的关键分支**：错误处理、权限判断是否被测到。
- **覆盖率突降**：说明新代码没写测试。

## 七、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 测试随机失败 | 依赖真实时间或随机数 | 用假时钟，注入可预期的依赖 |
| 改个无关代码测试就挂 | 断言了实现细节 | 改为断言对外行为 |
| 测试之间互相影响 | 共享可变状态 | 每个测试重建上下文（beforeEach） |
| 断言太宽泛 | 用 `toBeTruthy` | 断言具体值或结构 |
| 只测了成功路径 | 忽略异常分支 | 每个错误分支补一个用例 |

## 八、动手练习

1. 为第 03 章的 `groupBy`、`debounce`、`memoize` 各写一组测试（含边界）。
2. 把一个含真实时间的函数改成可注入时间，并为「过期」写测试。
3. 找出你项目里 mock 最多的一个测试，减少一半 mock。
4. 用覆盖率报告找出一个未覆盖的错误分支并补测试。
