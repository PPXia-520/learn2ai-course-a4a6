# 03 · 服务端框架实战

## 一、分层架构：让业务逻辑与框架解耦

```text
HTTP 请求
   ↓
路由 Router        只做：解析参数、调用 service、返回响应
   ↓
中间件 Middleware  横切关注点：认证、校验、日志、限流、错误处理
   ↓
服务 Service       业务规则与编排（事务边界通常在这里）
   ↓
数据访问 Repository 只负责读写数据库，不做业务判断
   ↓
数据库
```

见 `assets/node-request-lifecycle.svg`。这样分层的好处：service 可以用单元测试直接调用，不依赖 HTTP；换框架时业务代码不动。

```js
// routes/task.routes.js —— 薄薄一层，无业务逻辑
router.post('/', validate(createTaskSchema), async (req, res) => {
  const task = await taskService.create(req.body, req.user.id);
  res.status(201).location(`/api/v1/tasks/${task.id}`).json(task);
});
```

## 二、工程结构

```text
server/
  src/
    app.js               # 组装：中间件、路由、错误处理
    server.js            # 启动：监听端口、优雅关闭
    config/env.js        # 配置读取与校验
    middleware/
      auth.js
      validate.js
      error-handler.js
      request-logger.js
    modules/
      task/
        task.routes.js
        task.service.js
        task.repository.js
        task.schema.js
    shared/
      errors.js
      logger.js
      db.js
  tests/
```

**按业务模块分目录**（而非按技术分层平铺）能让一个功能的代码聚在一起，改需求时只动一个目录。

## 三、中间件：横切关注点

```js
// 请求日志：每个请求分配 id，贯穿全链路
app.use((req, res, next) => {
  req.id = req.headers['x-request-id'] ?? randomUUID();
  const start = process.hrtime.bigint();
  res.on('finish', () => {
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    logger.info({ requestId: req.id, method: req.method, path: req.originalUrl,
                  status: res.statusCode, durationMs: Math.round(ms) }, '请求完成');
  });
  next();
});

// 入参校验：schema 与运行时校验统一
export const validate = (schema, source = 'body') => (req, res, next) => {
  const result = schema.safeParse(req[source]);
  if (!result.success) {
    return next(new AppError('请求参数校验未通过', 422, 'VALIDATION_FAILED',
      result.error.issues.map(i => ({ field: i.path.join('.'), message: i.message }))));
  }
  req[source] = result.data;      // 用校验后的数据覆盖原始输入
  next();
};
```

中间件顺序很重要，推荐固定顺序：请求 id → 日志 → 安全头 → CORS → 解析体 → 限流 → 认证 → 路由 → 404 → 错误处理。

## 四、统一错误处理

```js
export function errorHandler(err, req, res, next) {
  if (err instanceof AppError) {
    return res.status(err.statusCode).json({
      error: { code: err.code, message: err.message, details: err.details, requestId: req.id },
    });
  }
  if (err.code === 'P2002') {                 // 唯一约束冲突（Prisma 示例）
    return res.status(409).json({
      error: { code: 'CONFLICT', message: '资源已存在', requestId: req.id },
    });
  }
  logger.error({ requestId: req.id, err }, '未预期的服务端错误');
  res.status(500).json({
    error: {
      code: 'INTERNAL_ERROR',
      message: '服务暂时不可用，请稍后重试',
      requestId: req.id,
      ...(config.isProd ? {} : { stack: err.stack }),   // 仅非生产环境返回堆栈
    },
  });
}

app.use(errorHandler);   // 必须放在所有路由之后
```

异步错误要能被捕获：用框架的异步包装，或用 `asyncHandler` 包装器把 reject 转成 `next(err)`。

## 五、其他必备中间件

| 关注点 | 做法 |
| --- | --- |
| 安全响应头 | 用 `helmet` 设置 CSP、`X-Content-Type-Options` 等 |
| 跨域 | `cors` 明确配置允许来源，不用通配符带上凭据 |
| 请求体大小 | 限制 `json({ limit: '100kb' })`，防止大体积攻击 |
| 限流 | 按 IP 与用户维度限流，返回 429 与 `Retry-After` |
| 压缩 | 只对文本类响应启用 gzip／br |
| 健康检查 | `GET /health` 返回进程与依赖状态，供负载均衡探活 |

## 六、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 错误处理中间件不生效 | 注册在路由之前 | 放到最后注册 |
| async 抛错导致请求挂起 | 未把 reject 交给 next | 用 asyncHandler 包装 |
| 校验后的数据没被使用 | 仍读取原始 `req.body` | 用校验结果覆盖 |
| 生产环境泄露堆栈 | 未按环境区分 | 仅非生产返回 stack |
| 日志无法串联一次请求 | 缺少 requestId | 生成并透传到所有日志 |
| 关服导致请求中断 | 无优雅关闭 | 见第 01 节 |
