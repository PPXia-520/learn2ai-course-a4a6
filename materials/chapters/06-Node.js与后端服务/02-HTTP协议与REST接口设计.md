# 02 · HTTP 协议与 REST 接口设计

## 一、一次请求到底长什么样

```http
POST /api/v1/tasks HTTP/1.1          ← 请求行：方法 + 路径 + 版本
Host: api.example.com                ← 请求头开始
Content-Type: application/json
Authorization: Bearer <token>
Idempotency-Key: 8f3c-...

{"title":"写周报"}                     ← 请求体

HTTP/1.1 201 Created                 ← 状态行
Location: /api/v1/tasks/41
Content-Type: application/json

{"id":41,"title":"写周报","status":"pending"}
```

记住四件事：**方法表达意图、路径表达资源、状态码表达结果、头表达元数据**。

## 二、方法与幂等性

| 方法 | 语义 | 幂等 | 请求体 | 成功状态码 |
| --- | --- | --- | --- | --- |
| GET | 读取资源 | 是 | 否 | 200 |
| POST | 创建资源／触发动作 | 否 | 是 | 201（创建）／202（异步受理） |
| PUT | 全量替换 | 是 | 是 | 200／204 |
| PATCH | 部分更新 | 通常否 | 是 | 200／204 |
| DELETE | 删除资源 | 是 | 否 | 204 |

**为什么关心幂等性**：网络会超时重试。删除和全量更新重复执行无副作用，而创建重复执行会产生两条记录——所以支付、下单这类接口要用 `Idempotency-Key` 做去重。

## 三、状态码的正确用法

| 码 | 含义 | 何时用 |
| --- | --- | --- |
| 200 | 成功 | GET／PUT／PATCH 成功返回数据 |
| 201 | 已创建 | POST 成功，响应带 `Location` |
| 202 | 已受理 | 任务进入队列，稍后异步完成 |
| 204 | 无内容 | DELETE 成功或无需返回体 |
| 301／308 | 永久重定向 | 域名或路径迁移 |
| 400 | 请求有误 | 参数格式错误、JSON 解析失败 |
| 401 | 未认证 | 未登录或令牌过期 |
| 403 | 无权限 | 已登录但没有操作权限 |
| 404 | 资源不存在 | 路径或 id 不存在 |
| 409 | 冲突 | 唯一约束冲突、并发修改 |
| 422 | 语义校验失败 | 字段格式正确但不满足业务规则 |
| 429 | 请求过多 | 触发限流 |
| 500 | 服务端错误 | 不可预期的异常 |
| 503 | 服务不可用 | 依赖故障、正在重启 |

**401 与 403 的区别**是老生常谈也最常写错的：401 是「你是谁我不知道」，403 是「我知道你是谁，但你不能做这件事」。

## 四、资源设计约定

| 约定 | 好 | 差 |
| --- | --- | --- |
| 用名词复数表示资源 | `/tasks` | `/getTasks` |
| 层级表达从属关系 | `/projects/7/tasks` | `/tasks?projectId=7`（浅层可选，深层必用层级） |
| 动作型操作用作子资源 | `POST /tasks/41/complete` | `POST /doComplete?task=41` |
| 过滤、排序、分页用查询串 | `/tasks?status=done&sort=-createdAt` | `/tasks/done` |
| 版本放在路径或头 | `/api/v1/tasks` | 不版本化 |

**分页三选一**：

| 方式 | 参数 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 偏移分页 | `?page=2&size=20` | 简单，可跳页 | 数据变动时会重复或漏项 |
| 游标分页 | `?cursor=abc&limit=20` | 稳定，适合信息流 | 不能随机跳页 |
| 键集分页 | `?after_id=1200` | 高效 | 需有序唯一键 |

响应里要给出下一步的信息，客户端才能可靠翻页：

```json
{
  "data": [ { "id": 41, "title":"写周报" } ],
  "pageInfo": { "nextCursor":"eyJpZCI6NDF9", "hasMore": true }
}
```

## 五、统一响应与错误结构

```json
{
  "error": {
    "code":"VALIDATION_FAILED",
    "message":"请求参数校验未通过",
    "details": [
      { "field":"title", "message":"不能为空" },
      { "field":"dueDate", "message":"必须晚于今天" }
    ],
    "requestId":"01J8Z..."
  }
}
```

三个原则：**错误码机器可判、消息人类可读、details 精确定位字段**；`requestId` 让用户报错时你能立刻查到日志。

## 六、接口设计的十条检查项

1. 路径用名词，方法表达动作。
2. 状态码与语义一致；创建返回 201 与 `Location`。
3. 所有输入都校验，错误精确到字段。
4. 分页、排序、过滤参数统一命名（`limit`／`cursor`／`sort`）。
5. 时间统一用 UTC ISO 8601（`2026-10-07T09:00:00Z`）。
6. 布尔与枚举取值明确，不用 `0/1` 或魔法字符串。
7. 大列表默认限流，避免一次拉全量。
8. 破坏性变更走新版本号，不偷偷改语义。
9. 接口有 OpenAPI 文档，且与实现同步。
10. 每个接口都有对应的集成测试（见第 09 章）。

## 七、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 用 200 返回错误信息 | 只依赖响应体判断成败 | 用状态码表达结果 |
| 404 与 403 混用 | 未区分未登录与无权限 | 401 认证、403 授权 |
| 重复提交产生两条数据 | 接口非幂等且未去重 | 幂等键 + 唯一约束 |
| 分页导致数据重复 | 偏移分页遇上插入删除 | 改游标分页 |
| 修改接口语义悄悄上线 | 未版本化 | 新版本路径或兼容层 |
| 返回体里带敏感字段 | 直接返回数据库实体 | 显式挑选字段（见第 08 章） |
