# 01 · 架构基础与设计原则

## 一、什么是架构

架构是**一组难以改变的决策**：技术选型、模块边界、数据归属、通信方式。好的架构让常见改动便宜、让错误暴露得早；坏的架构让每个需求都变成一场重构。

评价架构的三个问题：
1. **改一个需求要动几个模块？**（变更成本）
2. **一个模块坏了会影响多少功能？**（故障隔离）
3. **新人要多久能看懂并安全地改代码？**（可理解性）

## 二、分层与边界

```text
接口层（Controller/Route）    只做协议转换：解析入参、返回响应
  ↓
应用层（Service/UseCase）     编排流程、事务边界，不含 SQL
  ↓
领域层（Domain）              业务规则与不变量，纯逻辑、易测试
  ↓
基础设施层（Repository/Client）数据库、缓存、外部服务的具体实现
```

**依赖方向只能自上而下**，且下层通过接口被上层调用（依赖倒置）。这样领域逻辑不依赖框架、数据库，能独立测试与替换。

| 违反边界的信号 | 后果 |
| --- | --- |
| Service 里出现 `req`／`res` | 业务逻辑与 HTTP 绑死，无法复用 |
| 领域层直接 import ORM 实体 | 换存储要改业务代码 |
| 路由里写 SQL | 无法测试、无法复用、容易注入 |
| 模块之间互相 import 内部文件 | 改一处牵动全局 |

## 三、模块化与耦合度量

| 指标 | 含义 | 好的方向 |
| --- | --- | --- |
| 内聚（Cohesion） | 模块内元素的相关程度 | 越高越好 |
| 耦合（Coupling) | 模块之间的依赖强度 | 越低越好 |
| 扇入／扇出 | 被依赖数／依赖数 | 高扇入（被复用）好，高扇出（依赖太多）差 |
| 循环依赖 | A 依赖 B，B 又依赖 A | 必须消除 |

**拆模块的判据**：按**业务能力**拆（用户、订单、支付），而不是按技术类型拆（所有的 utils、所有的 models）。业务边界稳定，技术分层会随实现变化。

## 四、SOLID 五原则（务实版）

| 原则 | 含义 | 反例 |
| --- | --- | --- |
| 单一职责 | 一个模块只有一个变化的理由 | 一个 `UserService` 管认证、资料、通知、报表 |
| 开闭原则 | 对扩展开放、对修改关闭 | 每加一种支付方式都要改 `if/else` 大函数 |
| 里氏替换 | 子类型可替换父类型而不破坏行为 | 子类抛出不支持的异常 |
| 接口隔离 | 客户端只依赖它需要的方法 | 一个巨大的接口强迫实现空方法 |
| 依赖倒置 | 依赖抽象而非具体实现 | 业务层直接 new 数据库客户端 |

```ts
// 用「策略 + 注册表」替代不断膨胀的 if/else（开闭原则的落地）
type Notifier = { send(userId: string, msg: string): Promise<void> };
const notifiers: Record<Channel, Notifier> = {
  email: emailNotifier,
  sms: smsNotifier,
  push: pushNotifier,
};

async function notify(channel: Channel, userId: string, msg: string) {
  const n = notifiers[channel];
  if (!n) throw new AppError(`不支持的渠道：${channel}`, 400, 'UNSUPPORTED_CHANNEL');
  return n.send(userId, msg);
}
```

## 五、常用设计模式（按出现频率）

| 模式 | 解决的问题 | 典型场景 |
| --- | --- | --- |
| 策略 | 同一行为多种实现 | 支付、通知、折扣规则 |
| 工厂 | 创建逻辑集中 | 按类型构造客户端 |
| 装饰器 | 动态叠加能力 | 中间件、日志、缓存包装 |
| 观察者 | 一处变化、多处响应 | 事件总线、发布订阅 |
| 仓储 | 隔离数据访问细节 | Repository 层 |
| 适配器 | 统一不同外部接口 | 对接多个第三方 SDK |
| 单例（慎用） | 全局唯一实例 | 配置、连接池 |
| 状态机 | 复杂状态流转 | 订单状态、审批流 |

**原则**：模式是用来消除具体痛苦的，不是用来炫技的。先写出重复，再抽出模式。

## 六、状态管理的架构视角

| 类型 | 例子 | 复杂度来源 |
| --- | --- | --- |
| 领域状态 | 订单金额、库存 | 规则与不变量 |
| 会话状态 | 登录信息、购物车 | 一致性与过期 |
| 缓存状态 | 列表数据、统计 | 失效与一致性 |
| 事件状态 | 消息队列中的任务 | 幂等、重试、顺序 |

**减少状态是最好的优化**：能派生的就不要存，能无状态的就不要有状态（见第 02 节的无状态服务）。

## 七、常见架构坏味道

| 坏味道 | 表现 | 处理 |
| --- | --- | --- |
| 大泥球 | 任何模块都能改任何表 | 划定边界，禁止跨模块直连数据库 |
| 上帝对象 | 一个 service 2000 行 | 按用例拆分 |
| 循环依赖 | 编译／运行报错或隐式耦合 | 抽公共层或反转依赖 |
| 贫血领域 | 实体只有 getter/setter，规则散在 service | 把规则放回领域对象 |
| 过早抽象 | 只有一个实现的「接口层」 | 等出现第二个实现再抽象 |
| 隐式约定 | 靠口头约定而非类型与约束 | 写进类型、schema 与文档 |
