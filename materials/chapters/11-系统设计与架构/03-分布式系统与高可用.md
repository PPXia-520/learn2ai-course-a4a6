# 03 · 分布式系统与高可用

## 一、分布式带来的本质变化

把系统拆到多台机器后，出现了三个无法回避的事实：

1. **网络不可靠**：请求可能超时、重复、乱序到达，但你无法区分「对方没收到」和「对方处理了但响应丢了」。
2. **节点会挂**：任何组件都会在某个时刻不可用，包括你依赖的数据库。
3. **时钟不可信**：不同机器的时钟有偏差，不能用本地时间排序跨机事件。

**推论**：分布式系统的核心工作是**处理不确定性**——用幂等、重试、超时、补偿、去重来对抗它。

## 二、CAP 与一致性模型

CAP 说的是：网络分区（P）发生时，只能在一致性（C）与可用性（A）之间二选一。现实中 P 必然发生，所以真正的问题是：**分区时你要正确还是要可用？**

| 场景 | 倾向 | 做法 |
| --- | --- | --- |
| 支付、库存扣减 | CP：宁可不可用也不要错 | 强一致、加锁、失败重试 |
| 动态、点赞数、推荐 | AP：宁可短暂不准也要能用 | 最终一致、异步补偿 |

一致性谱系（从强到弱）：

| 级别 | 保证 | 例子 |
| --- | --- | --- |
| 线性一致 | 全局单一顺序，读到最新 | 单机强一致数据库 |
| 顺序一致 | 所有节点看到相同顺序 | 共识协议 |
| 因果一致 | 有因果关系的操作有序 | 社交评论 |
| 最终一致 | 最终收敛到一致 | 缓存、搜索索引、统计 |

**读己之写**是常见的用户体验要求：用户刚发的评论必须自己能看到。做法是把该用户后续读请求路由到主库，或本地缓存刚写入的记录。

## 三、幂等、重试与去重

```ts
// 幂等键：同一请求重复执行只生效一次
async function createOrder(idempotencyKey: string, input: OrderInput) {
  const existing = await repo.findByIdempotencyKey(idempotencyKey);
  if (existing) return existing;                    // 已处理过，直接返回原结果

  return db.transaction(async (tx) => {
    const order = await repo.create(tx, input);
    await repo.saveIdempotencyKey(tx, idempotencyKey, order.id);
    return order;
  });
}
```

| 措施 | 说明 |
| --- | --- |
| 幂等键 + 唯一约束 | 数据库兜底，避免并发下重复插入 |
| 指数退避重试 | 1s → 2s → 4s，加随机抖动避免同时重试 |
| 最大重试次数 + 死信 | 超过次数进入死信队列人工处理 |
| 只有可重试的错误才重试 | 参数错误重试一万次也没用 |

**重试的前提是幂等**：非幂等操作盲目重试会制造重复扣款、重复发货。

## 四、消息队列：解耦与削峰

| 特性 | 说明 | 设计要点 |
| --- | --- | --- |
| 解耦 | 生产者不关心消费者 | 定义清晰的事件契约（含版本） |
| 削峰 | 突发流量先进队列 | 队列深度是核心指标 |
| 异步 | 主流程不等待 | 关键结果仍需同步返回 |
| 顺序 | 同一分区内有序 | 用业务键做分区键 |
| 至少一次投递 | 可能重复 | 消费者必须幂等 |

```text
事件设计示例
topic: order.created
payload: { eventId, occurredAt, orderId, userId, amount, version: 1 }
约定：eventId 用于去重；version 用于兼容升级；occurredAt 由生产者提供（不依赖消费端时钟）
```

**不要用队列掩盖同步问题**：本该同步返回给用户的结果放进队列，只会让用户困惑。

## 五、微服务：何时该拆、何时不该拆

| 该拆的信号 | 不该拆的信号 |
| --- | --- |
| 团队按业务线独立交付，互相阻塞 | 只有一个 5 人以内的小团队 |
| 某模块需要独立扩缩容（如视频转码） | 流量远未到单机瓶颈 |
| 模块有独立的数据与生命周期 | 数据高度耦合、频繁跨模块事务 |
| 需要不同技术栈（如算法服务用 Python） | 只是为了「看起来先进」 |

拆开后的新问题：跨服务事务、调试难度、网络延迟、部署编排、契约管理。**微服务的成本是运维与协作成本，不是代码成本。**

分布式事务的现实做法：

| 方案 | 思路 | 适用 |
| --- | --- | --- |
| 本地消息表 | 业务与事件写在同一事务，再异步投递 | 最常用、最稳 |
| Saga | 拆成多步，失败则执行补偿动作 | 长流程（订单、旅行） |
| 两阶段提交 | 强一致但性能与可用性差 | 极少使用 |

## 六、高可用设计

| 层次 | 手段 |
| --- | --- |
| 接入层 | 多可用区负载均衡、健康检查、自动摘除故障节点 |
| 应用层 | 无状态 + 多实例 + 滚动发布；超时、熔断、限流、降级 |
| 数据层 | 主从复制、自动故障转移、定期备份与恢复演练 |
| 依赖层 | 隔离舱（不同依赖使用独立资源池）、缓存兜底 |
| 流程层 | 变更审批、灰度发布、快速回滚、故障演练 |

**单点排查清单**：DNS、负载均衡、网关、某个单实例服务、单台数据库、某个共享缓存、某个第三方依赖——逐个问「它挂了会怎样」。

**备份不等于可用**：没有验证过恢复流程的备份等于没有备份。要定期做恢复演练。

## 七、可观测性：三个支柱

| 支柱 | 回答的问题 | 关键实践 |
| --- | --- | --- |
| 日志 Logs | 发生了什么 | 结构化 JSON、requestId 贯穿、分级、脱敏 |
| 指标 Metrics | 系统健康吗 | 四黄金指标、按接口与依赖维度、分位数而非平均值 |
| 链路 Traces | 慢在哪一步 | 跨服务传播 traceId、记录每个 span 耗时 |

**为什么看分位数**：平均延迟 100ms 可能掩盖「1% 的用户等 5 秒」。p95／p99 才是体验的真实指标。

SLA／SLO／SLI 三件套：

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| SLI | 度量指标 | 成功请求比例 |
| SLO | 内部目标 | 月度可用性 ≥ 99.9% |
| SLA | 对外承诺（含赔付） | 低于 99.9% 按比例退款 |

## 八、故障处置流程

1. **止血**：回滚、限流、降级、切流——先恢复服务。
2. **评估影响**：影响多少用户、哪些功能、是否波及数据。
3. **定位根因**：用日志、指标、链路与变更记录（大多数故障由变更引起）。
4. **复盘**：写时间线与根因，产出可执行的改进项并跟踪落地。
5. **演练**：定期做故障演练，验证降级与回滚真的有效。

**复盘文化**：对事不对人。目标是让系统更健壮，而不是找谁负责。
