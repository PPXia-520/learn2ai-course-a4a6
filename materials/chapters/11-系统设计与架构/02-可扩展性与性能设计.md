# 02 · 可扩展性与性能设计

## 一、先估算，再设计

设计任何系统前，先算出量级。用「信封背面估算」把问题变具体：

```text
假设：日活 100 万，人均每天 20 次请求
日均请求 = 1000 万  →  平均 QPS ≈ 116
峰值假设为平均的 5 倍         →  峰值 QPS ≈ 600

假设每次请求产生 2KB 响应
出口带宽 ≈ 600 × 2KB ≈ 1.2MB/s（约 10Mbps）
```

**结论**：600 QPS 用「单体 + 读副本 + 缓存」完全够用。若不估算就上微服务，你只是在给自己制造复杂度。

| 估算项 | 公式 | 用途 |
| --- | --- | --- |
| QPS | 日请求 ÷ 86400，峰值 ×3~5 | 决定实例数与缓存策略 |
| 存储 | 单条大小 × 日增量 × 保留天数 | 决定分片与归档 |
| 带宽 | QPS × 响应大小 | 决定 CDN 与压缩 |
| 连接数 | QPS × 平均耗时（秒） | 决定连接池大小 |

## 二、扩展的两条路

| 方式 | 做法 | 上限 | 代价 |
| --- | --- | --- | --- |
| 纵向扩展 | 换更强的机器 | 受硬件上限约束 | 贵、有天花板 |
| 横向扩展 | 加更多机器 | 理论上无上限 | 需要无状态与负载均衡 |

横向扩展的前提是**无状态**：会话放 Redis 或令牌里，上传文件放对象存储，服务实例不保存本地状态。

## 三、性能优化的优先级顺序

```
1. 消除不必要的请求（缓存、合并、CDN）
2. 减少每次请求的工作量（索引、只查需要的字段、避免 N+1）
3. 让工作并行（并发请求、批量处理）
4. 异步化非关键路径（队列）
5. 最后才是加机器
```

**先优化最慢的一环**：用数据说话（延迟分位、慢查询日志、火焰图），而不是猜。

## 四、缓存：位置与策略

| 层 | 位置 | 典型收益 | 注意 |
| --- | --- | --- | --- |
| 浏览器缓存 | 客户端 | 减少请求总量 | 版本化与失效 |
| CDN | 边缘节点 | 静态资源与图片 | 缓存键与刷新 |
| 应用缓存 | 进程内（LRU） | 极快、无需网络 | 多实例不一致 |
| 分布式缓存 | Redis | 共享、容量大 | 序列化成本、网络往返 |
| 数据库缓存 | 查询缓存、物化视图 | 复杂聚合 | 刷新时机 |

**缓存三问**：缓存什么（读多写少）？什么时候失效（写后删除）？失效了会怎样（降级直查库）？

## 五、数据库扩展阶梯

| 阶段 | 手段 | 何时用 | 代价 |
| --- | --- | --- | --- |
| 1 | 加索引、优化 SQL | 一上来就该做 | 低 |
| 2 | 加缓存，挡住读流量 | 读多写少 | 一致性 |
| 3 | 读写分离（主从复制） | 读远多于写 | 复制延迟、可能读到旧数据 |
| 4 | 垂直分表（冷热分离） | 大字段拖慢查询 | 查询变复杂 |
| 5 | 水平分片（sharding） | 单表过亿或写入瓶颈 | 跨片查询、事务、扩容复杂 |
| 6 | 换存储（搜索、时序、图） | 特定查询模式 | 运维与一致性 |

**分片键的选择决定一切**：要保证数据均匀、查询能定位到单片（如按 `user_id` 分片，则「查某用户的所有订单」是单片的；而「查全站销量排行」需要额外方案）。

## 六、异步化与削峰

```text
同步：用户请求 → 通知邮件 + 生成报表 + 写库   （用户等 3 秒）
异步：用户请求 → 写库 + 投递事件（用户等 50ms）
                  ↓ 队列
              消费者：邮件、报表、统计（失败可重试）
```

| 场景 | 适合异步 | 不适合 |
| --- | --- | --- |
| 邮件／短信／推送 | 是 | — |
| 报表与统计 | 是 | — |
| 图片处理、转码 | 是 | — |
| 支付扣款结果 | — | 用户在等结果，需要同步确认 |
| 库存扣减 | 需谨慎 | 超卖风险，需强一致或补偿 |

**队列的四个必备设计**：幂等消费（重复投递不重复执行）、重试与退避、死信队列、监控积压。

## 七、限流、降级与熔断

| 手段 | 作用 | 实现要点 |
| --- | --- | --- |
| 限流 | 保护自己不被压垮 | 令牌桶／漏桶；按 IP、用户、接口维度 |
| 降级 | 核心功能优先 | 关闭非核心功能（推荐位、统计） |
| 熔断 | 防止被下游拖死 | 连续失败到阈值即快速失败，定期试探恢复 |
| 超时 | 兜住一切 | 每层调用都必须设超时，且上层超时大于下层 |

**没有超时的调用等于把命交给别人**：一个卡住的下游会迅速耗尽你的连接池。

## 八、常见性能陷阱

| 陷阱 | 表现 | 处理 |
| --- | --- | --- |
| N+1 查询 | 请求数随数据量线性增长 | 联表或批量加载 |
| 大事务 | 锁等待、复制延迟 | 事务只包数据库操作且尽量短 |
| 缓存雪崩 | 大量 key 同时失效 | 过期时间加随机抖动 |
| 无分页的全量查询 | 内存与带宽暴涨 | 强制分页并设上限 |
| 同步调用链过长 | 延迟叠加、放大故障 | 减少跳数，能并行则并行 |
| 热点 key | 单个 key 打爆单节点 | 本地缓存 + key 拆分 |

## 九、动手练习

1. 为一个「图片社交应用」做估算：QPS、存储、带宽，并写出你的假设。
2. 给一个慢接口做优化，按优先级顺序列出你尝试的四种手段与实测收益。
3. 设计一个「点赞数」的缓存与落库方案，说明如何避免丢数据。
4. 为你的 API 设计限流规则（维度、阈值、超限响应）。
