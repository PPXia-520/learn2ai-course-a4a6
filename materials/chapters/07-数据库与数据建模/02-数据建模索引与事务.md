# 02 · 数据建模、索引与事务

## 一、从业务到表：四步建模法

1. **列出名词**：用户、文章、评论、标签、订单……每个名词通常是一张表。
2. **确定关系与基数**：一对一、一对多、多对多（用中间表）。
3. **给每个字段定类型与约束**：能否为空、是否唯一、取值范围。
4. **为查询反推索引与冗余**：常用过滤／排序字段、需要冗余的计数字段。

## 二、规范化与反规范化

| 范式 | 要求 | 解决的问题 |
| --- | --- | --- |
| 1NF | 字段原子，不存重复组 | 一个单元格塞多个值 |
| 2NF | 非主键字段完全依赖主键 | 部分依赖导致的更新异常 |
| 3NF | 非主键字段不依赖其他非主键字段 | 传递依赖导致的更新不一致 |

```sql
-- 违反 3NF：city_name 依赖 city_id，而 city_id 依赖 user
-- 结果：城市改名要更新成千上万行
create table users_bad (id bigint primary key, city_id int, city_name text);

-- 3NF：城市名只存一份
create table cities (id int primary key, name text not null);
create table users (id bigint primary key, city_id int references cities(id));
```

**什么时候该反规范化**：读远多于写、且能接受短暂不一致时。典型做法是**冗余派生列**并明确它的权威来源：

| 反规范化手段 | 例子 | 一致性保障 |
| --- | --- | --- |
| 冗余计数 | `posts.comment_count` | 写评论时在同一事务里更新 |
| 冗余展示字段 | 订单冗余下单时的商品名与价格 | 快照语义，故意不跟随变化 |
| 物化视图 | 报表汇总 | 定时刷新 |

## 三、索引：原理与代价

索引是额外的数据结构（PostgreSQL 默认 B-tree），让「查找」从 O(n) 变成 O(log n)。**代价**：占空间、每次写入要维护、过多索引会拖慢插入更新。

```sql
create index idx_posts_author_published
  on posts (author_id, published_at desc)
  where status = 'published';             -- 部分索引：只索引需要的行

create unique index uq_users_email on users (lower(email));   -- 大小写不敏感唯一
create index idx_posts_title_trgm on posts using gin (title gin_trgm_ops);  -- 模糊搜索
```

| 索引类型 | 适用 |
| --- | --- |
| B-tree（默认） | 等值、范围、排序、前缀匹配 |
| Hash | 仅等值查询 |
| GIN | 数组、JSONB、全文检索 |
| GiST | 地理、区间 |
| BRIN | 超大表的顺序字段（如时间） |

### 最左前缀原则

复合索引 `(a, b, c)` 能服务 `a`、`(a,b)`、`(a,b,c)` 的查询，但**不能**直接服务只按 `b` 或 `c` 的查询。

| 查询条件 | 能否用上 `(author_id, published_at)` |
| --- | --- |
| `where author_id = 7` | 能 |
| `where author_id = 7 order by published_at desc` | 能（且免排序） |
| `where published_at > '2026-01-01'` | 不能（跳过最左列） |

### 用 EXPLAIN 验证，而不是猜

```sql
explain (analyze, buffers)
select id, title from posts
where author_id = 7 and status = 'published'
order by published_at desc
limit 20;
```

看三个关键点：是否出现 `Seq Scan`（大表顺序扫描通常是坏信号）、`rows` 预估与实际差多少（差太多说明统计信息过期，需 `analyze`）、以及是否出现了额外的 `Sort`（说明索引没覆盖排序）。

## 四、事务与隔离级别

```sql
begin;

-- 悲观锁：把这行锁住，别人只能等
select balance from accounts where id = 1 for update;
update accounts set balance = balance - 100 where id = 1;
update accounts set balance = balance + 100 where id = 2;

commit;      -- 任一步失败则 rollback
```

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
| --- | --- | --- | --- | --- |
| Read Uncommitted | 可能 | 可能 | 可能 | 极少使用 |
| Read Committed | 否 | 可能 | 可能 | PostgreSQL 默认 |
| Repeatable Read | 否 | 否 | 否（PG 实现） | 需要一致性快照时用 |
| Serializable | 否 | 否 | 否 | 最强，冲突时需重试 |

**并发写冲突的两种解法**：

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 悲观锁 | `select ... for update` 先锁再改 | 冲突频繁、事务短小 |
| 乐观锁 | 带 `version` 字段更新，`where version = n` | 冲突稀少、读多写少 |

```sql
-- 乐观锁：影响行数为 0 说明有人先改了
update documents
set content = $1, version = version + 1
where id = $2 and version = $3;
-- 应用层判断 rowCount === 1，否则返回 409 让用户重新加载
```

## 五、常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 索引建了却没被用 | 类型不匹配、函数包裹列、跳过最左列 | 让条件与索引类型一致，必要时建表达式索引 |
| 事务长时间不提交 | 应用层有长耗时操作 | 事务只包住数据库操作 |
| 死锁 | 两个事务加锁顺序相反 | 统一加锁顺序，缩短事务 |
| 计数不准 | 并发下先查后写 | 用数据库原子更新或事务 + 行锁 |
| 数据量涨了才变慢 | 统计信息过期 | 定期 `analyze`，关注慢查询日志 |
